## 本任务相关补充事实

- 当前 `quality_check` 只读取宽高、时长、供应商、上游状态等元数据，实际看不到视频内容。
- 当前质量智能体明确禁止因为“看不到媒体”而失败，因此不能检测脸部漂移、手脚畸变或动作断裂。
- 当前 H3 生成结果已存入对象存储，可以通过受控签名 URL 交给后端分析服务。
- 角色库提供参考图，场景库提供参考素材，可作为候选质量比较依据。
- 当前质量档为 `preview`、`standard`、`cinematic`，候选数应已由 P0-02 固定为 1/2/3。
- 当前生产容器没有 GPU 环境，独立分析模型必须走 P0-03 的协议。

## 目标

把质量判断升级为真正读取视频内容的可解释分析，检测人物身份漂移、肢体异常、多人身份交换、动作跳变、闪烁及基础技术错误，并对候选进行确定性排序。

## 分析能力基线

处理器配置应能登记下列能力和制品版本，但本任务不下载或运行这些权重：

- FFmpeg/PyAV：解码、时长、帧率、黑帧、音轨和抽帧。
- ByteTrack：多人跨帧跟踪。
- OpenVINO 人脸检测、关键点、`face-reidentification-retail-0095`：身份比较。
- DWPose 或 MMPose WholeBody：身体、脸、手、脚关键点。
- SEA-RAFT：光流和运动连续性。

不得把某一实现写死为唯一供应商；工作流依赖的是分析能力与报告合同。

## 必须实现

1. 定义版本化 `VideoQualityReport`，至少包含：
   - `schema_version`、分析器和制品版本；
   - `technical`；
   - `person_tracks`；
   - `face_identity`；
   - `pose_motion`；
   - `temporal`；
   - `defects`；
   - `decision`、维度分数和总分。
2. 每项缺陷至少包含：
   - 稳定缺陷类型；
   - `severity`、`confidence`；
   - 开始和结束时间；
   - `track_id` 和可选角色 ID；
   - bbox、轨迹或 mask 制品引用；
   - 推荐动作及理由。
3. 多人轨迹与角色参考图必须通过明确匹配结果关联；无法可靠匹配时标记 `unknown`，不能根据站位或角色名猜测。
4. 至少支持下列问题类型：
   - 视频无法解码、时长错误、黑帧、预期音轨缺失；
   - 身份相似度持续下降或突降；
   - 人脸检测覆盖异常和相邻帧五官闪变；
   - 骨长突变、孤立左右肢体翻转、手脚关键点持续丢失；
   - 关节速度/加速度异常；
   - 前景人物与背景非预期滑动、光流不连续和闪烁；
   - 多人轨迹身份交换。
5. 脸部太小、侧脸、背脸、强遮挡和离开画面必须标记为 `not_assessable` 或 `unknown`，不能自动判定身份失败。
6. 阈值按分析器、模型 revision、画面类型和校准集配置，不使用跨模型通用余弦阈值；报告必须写入实际采用的阈值版本。
7. 候选排序采用代码中的确定性规则：
   - 技术硬失败候选不可推荐；
   - 严重且高置信缺陷优先淘汰；
   - 再比较身份、姿态、时序和提示一致性；
   - 完全并列时按候选序号稳定选择。
8. LLM 质量智能体只能解释结构化报告、生成用户可读说明和返工建议，不能覆盖技术硬门禁或修改原始检测数据。
9. 分析失败的降级策略：
   - `preview` 可保留候选并标记未完成内容质检；
   - `standard/cinematic` 不得伪装为已通过，必须显示需要人工审核或分析器不可用；
   - 不得因分析服务临时失败自动再次产生收费视频候选。
10. 报告和缺陷时间码应能通过 API 返回，但原始嵌入向量、内部 mask 路径和分析服务签名 URL 不对 C 端暴露。

## 测试与验收

- 使用固定模拟报告覆盖：近景、全身、双人遮挡、三至四人、低光、快速转身、手持物和快运镜。
- 验证硬门禁、严重缺陷、unknown/not_assessable、身份交换时间码、稳定并列排序。
- 验证 LLM 解释器无法将硬失败改成通过。
- 验证分析器同步、异步、超时、失败和版本不匹配的降级路径。
- 验证报告不泄露嵌入向量、签名 URL、密钥或内部路径。
- 通过模拟标签计算严重缺陷召回率、误拒率和候选排序统计，但明确它们不是实际模型指标。
