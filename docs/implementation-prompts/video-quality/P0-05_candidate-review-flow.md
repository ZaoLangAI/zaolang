## 目标

让用户比较原始候选和后续增强/修复候选，查看问题时间码，选择、批准、请求修复或拒绝；自动推荐只提供建议，不代替 standard/cinematic 的人工终审。

## 必须实现

1. 新增或扩展 API：
   - `GET /v1/generation-jobs/{job_id}/candidates`；
   - `POST /v1/generation-jobs/{job_id}/review`。
2. 审核动作固定为：
   - `approve`；
   - `select_candidate`；
   - `request_repair`；
   - `reject`。
   使用有界 Pydantic schema，拒绝未知动作和跨作业候选。
3. 新增追加式审核记录，至少保存：
   - job、candidate、用户、动作、原因；
   - 对应质量报告版本；
   - 上一审核记录和时间戳。
   重新选择必须新增记录，不能覆盖历史判断。
4. 生成任务在候选生成、质检和推荐完成后按正常路径结算为 `SUCCEEDED`；人工审核是成功后的独立状态，不新增长期占用积分的非终态。
5. `preview` 默认允许采用自动推荐候选；`standard/cinematic` 在没有有效人工批准记录前：
   - 不得发布；
   - 不得作为短剧 canonical work；
   - 不得自动进入编辑器主轨；
   - 可以在候选审核页预览。
6. `output_asset_id` 继续表示生成时的自动推荐候选以保持旧 API 兼容；实际编辑/发布选择应优先读取最新有效人工审核记录。
7. `request_repair` 只创建结构化返工请求或进入已发布的修复工作流，不得在本任务中伪造修复结果。
8. 审核页面至少显示：
   - 候选播放器和候选切换；
   - 自动推荐、人工已选、原始/子候选标记；
   - 身份、动作、时序、技术维度；
   - 缺陷列表、时间码和对应人物；
   - 分析不可用或 `unknown` 的明确状态；
   - 请求修复、选择和批准操作。
9. 如果同步播放器实现复杂，首期可以采用单播放器 + 快速候选切换，但必须保持相同播放时间位置；不能假装同时播放已实现。
10. 权限要求：
    - 只有作业所有者或具备明确后台权限者可审核；
    - 候选必须属于该作业；
    - 其他剧集、已清理、不可用或无权访问资产不能被选择；
    - 重复幂等请求不能产生重复审核记录。
11. 发布、编辑器入口和剧集内容关联必须统一调用同一审核解析服务，不能在不同 API 中各自判断。

- 候选列表只返回当前用户可访问作业的数据。
- 自动推荐、人工选择、重新选择和追加历史正确。
- `preview` 兼容旧直接使用行为。
- `standard/cinematic` 在未批准时被发布、canonical work 和编辑器主轨统一拒绝。
- 审核后编辑器和发布读取相同候选。
- `request_repair` 不直接修改现有候选或质量报告。
- 未授权、跨作业、已清理候选、重复幂等请求和并发选择均有确定结果。
- 前端键盘操作、加载/错误/空状态和多语言文本有测试。
