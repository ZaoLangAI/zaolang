# Drama Editor

## Scope

Both the product surface and the editing engine live in this repo. The only thing exposed externally is `EditCommand` and the canonical timeline — never expose an external editor's own project/element types through the API.

A drama `Series` now has a **second** creative surface beside the timeline: `GET /v1/drama-series/{series_id}/canvas` resolves-or-creates that series' infinite canvas, which reads the same `Series`/`DramaEpisode` rows through its own routes and its own concurrency model. Anything about the canvas itself — its tables, `/graph-ops`, the change stream, its Agent — is `zaolang-canvas`, not here.

## Invariants

1. **Time is expressed in integer ticks**, `120000 ticks = 1s`, validated against the JS safe-integer range. Floating-point seconds are forbidden.
2. **The canonical document lives server-side**, in `cut_revisions.document_json`. MCP's `apply_edit_plan` doesn't depend on any open browser tab.
3. **MCP's `project_id` equals `Series.id`** (`kind=drama`). Don't build a new Project table — `Series` here is a reuse of the character-roster table, not a second episode model.
4. **There is no `/v1/series` route any more — the `kind=cast` roster CRUD it exposed was deleted along with `ShortformStudio`.** `Series(kind=cast)` rows created before this change were purged by migration `ada14f32676f` (`20260829_1001_purge_orphaned_cast_series_rows.py`); `SeriesKind.CAST` stays on the enum and the column was not dropped (`zaolang-data-model` invariant #8 still applies to the shared table), but nothing can create, list, or edit a cast row any more, every remaining `Series` creation path passes `kind=drama` explicitly, and `characters.service.delete_character` no longer touches `character_ids_json` at all — it just deletes the `CreationSkill`. The create hub's "最近短剧" rail and `/create/short` both read `kind=drama` rows from `/v1/drama-series` now (`front/src/components/create/recent-series.tsx`) — don't reintroduce a cast-series read path for either.
5. **Only *creating/listing a `Series` row* is split by `kind`; episode writes underneath it are not.** `from-job` may still auto-create a `kind=drama` series (and a new episode under it) **only when the job's draft has no `link_episode_id`** — that is the "jumped straight from a generation job into 进入剪辑" fallback. A script-studio video jump-out already writes `params.link_episode_id` on the draft; `create_cut_from_job` must attach the cut to that existing episode and must not mint a second series or episode. A present-but-foreign id is a 4xx, not a fall-through into the shell-creating path. A present id whose `DramaEpisode` row is gone (the user deleted the episode) is stale: clear the draft param and fall through so 进入剪辑 is not permanently 404. **`from-job` is get-or-create on the episode's primary cut** (`kind=full`, name `主剪辑`, unique as `uq_episode_cuts_episode_kind_name`): a later succeeded job on the same draft — or a second click on the same job — must return the existing cut, never INSERT a second "主剪辑" (that unique violation used to 500). The episode panel already reused `cuts[0]`; keep the two entry points aligned. The roster API must never write a drama `Series` row — but `DramaEpisode`/`EpisodeContentLink` CRUD no longer requires `kind=drama` at all (see invariant #17). Don't reintroduce a `require_drama_series` check on basic episode create/list/update/content-link/canonical-work calls; that check is now reserved for the timeline-editor entry points (`create_cut_from_job` and beyond) that actually need a production project's extra fields.
6. **Leases have a single writer**: conditional updates, and a terminal lease can't be reopened by a heartbeat. Losing a lease degrades to read-only rather than overwriting a newer head.
7. **A failed command batch rolls back entirely**, leaving head unchanged. Writing a revision requires `expected_revision_id` for CAS.
8. **Internal editing revisions never write a `LineageEdge`.** Publishing must bind to an explicitly successful `EditorExport.output_asset_id`; the entry point is not PublishKit.
9. **Manual editing and browser export are free.** AI planning only records an `AgentRun` and never touches ledger unique keys.
10. **`web_editor_enabled` / `variant_export_enabled` / `editor_ai_enabled` / `editor_mcp_enabled` default to false and gate the timeline editor** (cuts/leases/revisions/exports/AI planning/MCP); export/AI/MCP all depend on `web_editor_enabled`; off means 404. Local `make seed` flips all four on — production defaults to off. **`drama_studio_enabled`/`FLAG_DRAMA` is defined but no longer enforced anywhere** — `create_drama_series`/`list_drama_series` used to gate on it but that check was removed once `/v1/drama-series` became the single, publicly-unified series/episode surface (see invariant #17); don't reintroduce it there.
11. **MCP's audience is always `mcp`.** Consumer and admin tokens are rejected. There is no publish tool. The exclusion originally existed to keep `kind=cast` rosters — those rows have since been purged (invariant #4), so today there is no cast roster left to preserve; the `DELETE ... 16. **`script_studio_enabled` is its own flag, deliberately not `drama_studio_enabled`.** Script writing can ship (or be turned off) independently of the full editor, even though `prepare_new_script`/`prepare_turn` write to the same `series`/`drama_episodes` tables `create_episode` does. `script_writing.service` gates every entry point on `script_studio_enabled` via its own `_require_script_studio`, and mints the `DramaEpisode` (and, without a `seriesId`, the `Series(kind=drama)` shell) itself rather than calling `editor_service.create_episode` — not because the latter is flag-gated (it isn't: `create_episode` resolves through `_accessible_series` and never calls `editor_flags.require_flag`, see invariant #17/#27) but because script writing also needs to compute the next `season_number == 1` episode number, store `source_idea`, and fire the `script` notification in the same transaction. `DramaEpisode.script_json` always holds the *latest* turn's script; `episode_script_turns` is what makes history browsable. A script written this way is a normal `DramaEpisode` — it can later be opened in the drama editor to generate cuts from.
17. **Series/episode/content-link CRUD lives on exactly one route family now — `/v1/drama-series`+`/v1/drama-episodes` (`api/v1/editor.py`) — and none of it is flag-gated.** `api/v1/characters.py` used to mount a second, parallel copy at `/v1/series/{id}/episodes(/{episode_id})` (same `editor_service` calls, `_owned_series_episode` re-checking the path's `series_id`/`episode_id` pair) so a plain `kind=cast` roster series could manage episodes without `create_drama_series`'s old `FLAG_DRAMA` gate; that mount has been deleted (it had no real frontend caller) and `FLAG_DRAMA`'s two enforcement call sites (`create_drama_series`/`list_drama_series`) were removed instead, so `/v1/drama-series` is now open to any authenticated user regardless of kind. **Don't re-add either** — a second mount or a reinstated `FLAG_DRAMA` check would recreate the exact duplication this consolidation removed. `editor_service.create_episode`/`list_episodes`/`get_episode`/`update_episode`/`delete_episode`/`create_content_link`/`list_content_links`/`delete_content_link`/`set_canonical_work` all resolve access through the shared `_accessible_series`/`_accessible_episode` helpers (owner or active `SeriesCollaborator`, no `SeriesKind` filter at all, unlike `require_drama_series`) and never call `editor_flags.require_flag` — the episode model is kind-agnostic, so nothing here depends on `kind=drama`. `create_episode` accepts `season_number` (default `1`) and `episode_kind` (default `EpisodeKind.MAIN`); a season/episode-number collision inside the same series raises `ValidationFailed` (422), scoped by `(series_id, season_number, episode_number)` — a trailer or a second season doesn't collide with episode 1. `create_content_link` traces `content_ref_id` back to its owner by hand per `content_type` (`_content_owner_user_id`: `Draft.user_id` / `Work.owner_user_id` / walking `EditorExport → DeliveryVariant → CutRevision → EpisodeCut → DramaEpisode → Series.owner_user_id`) since it isn't a real foreign key — linking someone else's content is `Forbidden` (403), a non-existent ref is `NotFound` (404); linking the same `(episode_id, content_type, content_ref_id)` twice updates the existing row's `role` in place rather than duplicating it (the table's own unique constraint backs this). When `content_type=draft`, it also calls `_seed_draft_link_episode_id`: write `params.link_episode_id` **only if the draft has none yet**, so a script-studio jump-out stays bound to its episode and a post-hoc "关联到剧集" / "添加已有视频" still stops `from-job` from minting a second series. `set_canonical_work` writes `DramaEpisode.canonical_work_id` directly (what publishing/the public projection actually trust) and also upserts a `role=final` `EpisodeContentLink` as a history breadcrumb — passing `work_id=None` clears both. Only entering the full timeline editor (`create_cut_from_job`/`acquire_lease`/`apply_commands`/exports/AI planning) still requires `FLAG_EDITOR`/`FLAG_EXPORT`/`FLAG_AI`/`FLAG_MCP` and, for `from-job`'s drama-series auto-create path, `require_drama_series`'s `kind=drama` check. On the frontend, `GenerationSubmitInput.linkEpisodeId` (`use-generation-submit.ts`) is a deep-link convention mirroring the script studio's `returnTo`/`returnLinkKind` one (`zaolang-frontend-ui` invariant #16): a caller appends `?linkEpisodeId=` to `/create/new`, and `POST /v1/drafts` writes that onto `params.link_episode_id`. `publishing.create_draft` then best-effort inserts a `candidate` content-link in the same transaction (`content_type=draft`); a missing or foreign episode is swallowed and never blocks the draft, since the content-link list is a convenience view, not the source of truth for what the draft is. `list_content_links` also heals historical drafts that already carry `params.link_episode_id` but never got a row (the write path used to persist the param only). A standalone video that was never jumped out of 文案创作 can still be attached afterwards: `InlineVideoResult`'s "关联到剧集" (`link-episode-dialog.tsx`) and the episode panel's "添加已有视频" (`attach-generated-video-dialog.tsx`) both call the same `createContentLink`. iOS has no content-link client this round.
18. **An unpublished editor graph can be torn down with the episode.** `delete_episode` (and `delete_script`) call `purge_unpublished_editor_graph`: unpublished cuts / revisions / variants / unbound exports go away in `RESTRICT`-safe order; `canonical_work_id` or a bound draft with `published_work_id` is 422. `CutRevision.parent_revision_id` is a self-`RESTRICT` — delete by `revision_no` descending and **flush each row**; a batched `DELETE` ignores Python order and 500s once a cut has two revisions. Works / jobs / assets / sibling episodes / the series stay. There is no `DELETE /v1/episode-cuts/{id}`. **A single 最终成片 row** is `DELETE /v1/editor-exports/{id}` (`exports.delete_export`): owner-only via `_owned_export`, terminal statuses only (in-flight is 422 — cancel first), a published bind or a `WorkVersion` already stamped with that export is 422, the bound draft is unbound (not deleted), and the output asset / delivery variant stay. `from-job` writes a `candidate` draft content-link (and `params.link_episode_id` when missing) so the episode workspace is not an empty shell. Do not write "entered the editor, can never delete."
19. **Tracks are no longer fixed at exactly 4, and audio is real now.** `document.py`'s schema carries `order`/`label`/`muted` per track (backfilled transparently for old revisions by `canonicalize()`'s `_normalize_track` — no `SCHEMA_VERSION` bump, since revisions are immutable snapshots with no migration path); `commands.py` adds `add_track`/`remove_track`/`set_track_order`/`set_track_muted`, capped at `MAX_TRACKS_PER_KIND = 16` per kind. Only `video`/`audio` tracks (`TRACK_KINDS_ADDABLE`) can be added or removed — `trk_caption`/`trk_overlay` remain permanent singletons, `remove_track` rejects them outright, and rejects removing the last track of a kind or a non-empty track. `insert_clip`/`insert_caption`/`move_elements`'s cross-track target now all check `track.kind` matches (video/audio for clips, caption for captions, same-kind only for moves) — this didn't matter with 4 fixed tracks but does now that tracks are user/AI-created. The frontend compositor (`compositor.ts`'s `activeVideoLayer`, exported) picks the topmost non-muted video track with an active clip at the current tick (`order` descending, first match wins) — lower tracks are neither drawn nor heard while a higher one covers them. **Audio is now real, on both preview and export, built on the same `resolveAudioLayers(document, atTicks)`** (every non-muted audio track's active clip, plus the *currently visible* video track's own embedded sound — a hidden/occluded video track stays silent too, matching what's shown): live preview (`engine/audio-mixer.ts`'s `AudioMixer`) schedules decoded `AudioBufferSourceNode`s per active layer instead of reseeking a playing element every animation frame (the reseek-per-frame model `compositor.ts`'s `seekVideo` still uses for picture is exactly why audio used to be muted — buffer scheduling sidesteps that glitch); export (`export-runner.ts`'s `renderMixedAudio`) mixes the same layers offline via `OfflineAudioContext` at document breakpoints (every element start/end tick, since the active-layer set only changes there) and adds a second `mediabunny` track via `AudioBufferSource`/`output.addAudioTrack()` — which **must be registered before `output.start()`**, so export decides synchronously (`documentHasAudibleContent`) whether to add the track at all, then fills it in after the picture loop. Speed changes shift audio pitch (`playbackRate`, no time-stretch) — same tradeoff `set_clip_speed` already accepts for picture, now extended to sound.
20. **A script turn's SSE stream can only report failure inside the stream itself.** By the time a turn fails (a bad model reply, a DB error), the `200`/`202` header and `delta` frames are already sent — there is no HTTP status left to change, so the route emits `event: error` as the last frame instead. `app.domain.script_writing.service` opens its own DB session per turn via `session_scope()` (a request-scoped `DbSession` is already closed by the time a `StreamingResponse` generator runs), and every exception path there must `session.rollback()` before returning — skipping it leaves the session unable to commit, which raises `PendingRollbackError` while the generator is closing and kills the stream with no closing frame at all instead of a clean `error` event.
21. **Clip effects/masks exist, with a deliberately closed, empirically-verified allowlist — never open it up on assumption.** `commands.py`'s `EFFECT_TYPES = {"blur", "brightness", "contrast", "saturate", "grayscale"}` and `MASK_SHAPES = {"rect", "ellipse"}` (mirrored in `canonical.ts`) aren't a placeholder subset of some larger OpenCut effect catalog — they're the actual, tested ceiling of what this repo's rendering paths can do. `blur` alone is GPU-accelerated through the vendored WASM module's real `gaussian-blur` shader (`front/src/features/editor/engine/wasm-compositor.ts`'s `applyBlur`, calling `applyEffectPasses`) — confirmed working by direct empirical test (upload a sharp test pattern, call `applyEffectPasses`/`applyMaskFeather`, read the pixels back via `drawImage` onto a fresh 2D canvas since the WASM output canvas already owns its own GPU context) against `third_party/opencut-classic/rust/crates/effects/src/pipeline.rs`, which — at the pinned vendored commit — has **only** `gaussian-blur` actually registered; every other effect type, and blur's own fallback when WASM is unavailable, is a plain Canvas2D `ctx.filter` (`front/src/features/editor/engine/effects.ts`). Masks *always* use Canvas2D feathering (a transparent-background alpha shape blurred via `ctx.filter`, composited with `destination-in`) even when WASM is available — `applyMaskFeather` is confirmed working too, but it feathers luminance, not alpha, and using it here would need a per-frame CPU readback that risks preview frame rate; not worth it for what CSS blur already does well. Adding a new effect type means it either has a real shader registered in the vendored Rust pipeline (verify by the same empirical method before trusting `docs/effects-renderer.md`'s architecture description — that doc describes the *pattern* for adding effects, not which ones are actually built at this commit) or is CSS-filter-expressible; don't add a type to the allowlist on the assumption that "OpenCut probably has this."
22. **A shallow element copy must deep-copy `effects` and `animations.channels` — `_split_element`/`split_element` learned this the hard way, twice.** `dict(element)` (Python) / `{...element}` (TS) still shares the `effects` array (and every effect object in it), and the `animations.channels` map, with the original. `add_effect`/`remove_effect` reassign the array so they self-heal after first use, but `update_effect_params` mutates an effect object's `params` in place, and `set_keyframe`/`delete_keyframe`/`clear_keyframes` mutate a key on the shared `channels` dict in place — without an explicit deep copy at the split site (`effects: [dict(e) for e in element.get("effects") or []]` + a matching per-property copy of `animations["channels"]` on the backend; `effects.map((e) => ({...e}))` + a matching `Object.fromEntries`-built `channels` copy on the frontend), editing one half silently corrupted the other. `mask` needs no equivalent treatment: every write to it replaces the whole value, never mutates in place. **Any future per-element field that gets mutated in place by its own commands (not wholesale-replaced) needs the same treatment added to `_split_element` — this is a recurring class of bug, not a one-off.**
23. **`set_keyframe`'s `property` field is a closed, server-validated enum — not the generic path/value update `validate_batch` permanently forbids** (`commands.py`'s `if "path" in raw or command_type == "update_property": raise ValidationFailed(...)`). `ANIMATABLE_PROPERTIES = {"opacity", "transform.x_milli", "transform.y_milli", "transform.scale_millipercent", "transform.rotation_millidegrees", "volume"}` (mirrored in `canonical.ts`) is the entire addressable surface; each has its own numeric range in `PROPERTY_RANGES`, checked before the value is ever stored — `volume` uses `(0, 200_000)`, the same millipercent range `set_clip_volume` accepts, because a volume keyframe channel is a time-varying way to drive that same value, not a separate concept. Each keyframe may also carry an `easing` drawn from the closed `EASING_TYPES = {"linear", "ease_in", "ease_out"}` (`DEFAULT_EASING = "linear"`), validated on `set_keyframe` on both sides for the same reason the property list is closed. This reads structurally like a path updater (a string selecting *which* field to touch) but isn't one in the sense the ban cares about: it can never reach an arbitrary tree location, only one of six pre-approved leaf properties, each with bounds-checked values — the same shape `set_clip_volume`/`set_clip_speed` already use for their own single field, just parameterized over a few names instead of hardcoded to one. **Don't extend `ANIMATABLE_PROPERTIES` to accept a caller-supplied path string** — adding a new animatable property means adding its name to this frozenset/Set and a range to `PROPERTY_RANGES` by hand, on both sides (another 3-way-sync-adjacent edit, though not a new `EditCommand` type), not making the field open-ended. Keyframes are deliberately coarse (hand-placed points, not per-frame data) — `resolveNumberAtTime` (`engine/animation.ts`) linearly interpolates between them and holds the edge value outside the range; there is no diff-based revision storage or externalized keyframe blob store, because at this density a document's keyframe data stays negligible against the existing 5MB/5000-element caps (`time.py`) — don't add either without a real, measured reason first.
24. **Stickers are not a new element shape — `insert_clip`'s optional `element_type: "clip" | "sticker"` (`ELEMENT_TYPES_ADDABLE`, mirrored in `canonical.ts`) just sets `TimelineElement.type`, which was already `'clip' | 'caption' | 'brand'` before this and is now `| 'sticker'` too.** A sticker is otherwise a completely ordinary clip element — same effects/mask/keyframe/transition fields, same track kind restriction (`TRACK_KINDS_ADDABLE`, video/audio only — there is no dedicated sticker track), positioned/animated via the exact same `transform.*` keyframe channels any clip has. Don't add a parallel `insert_sticker` command or a `sticker_provider`/sticker-pack field — this platform has no curated sticker asset library, so a sticker is just any of the user's own image assets (`media-library-panel.tsx`'s `MediaCard` offers "插入为贴纸" only for `media_type === 'image'` items), inserted with `element_type: 'sticker'` instead of the default.
25. **Transitions live on a clip's own `transition_in`/`transition_out` fields, never as a new element, track, or command targeting two elements at once.** `set_transition {element_id, edge: "in"|"out", transition: {type: "crossfade"|"dip_to_black", duration_ticks} | null}` only ever touches the ONE element named — the actual blend only happens when the adjacent clip on the *same track* is made to overlap it in time via ordinary `trim_element`/`move_elements` (no new mechanism creates the overlap itself). `duration_ticks` is validated against the element's own `duration_ticks` at write time (`transition.duration_ticks <= element.duration_ticks`), not against the actual overlap span — that's checked separately, at render time. **Resolution lives in `compositor.ts`'s `resolveOverlap`, the one place two same-track elements are allowed to both be "active" at the same tick** (`activeElementsOnTrack` returns however many overlap, not just the first `.find()` match — this is new: before Phase 4, exactly one element per track could ever be active at a tick). The effective transition is whichever of the *outgoing* clip's (earlier `start_ticks`) `transition_out` or the *incoming* clip's `transition_in` is set — outgoing wins if both are configured, and an overlap with **neither** configured falls back to "the newer clip wins" rather than a silent double-exposure (this is also what an ordinary same-track drag-to-overlap-without-configuring-a-transition looks like — don't treat it as an error state). `crossfade` renders both clips at once with complementary alpha weights (`FrameLayers.transitionLayer`, drawn on top of `FrameLayers.clip` in `composeFrame` via the shared `renderClipLayer` helper — same seek/WASM-or-Canvas2D/effects/mask/transform pipeline, just called twice in one frame). `dip_to_black` **never** produces a `transitionLayer` — it shows exactly one clip at a time, fading it out to nothing then the other in from nothing, by design (never blends two pictures together). Split correctness: `_split_element`/`split_element` set the new internal cut point's `transition_in`/`transition_out` to `null` on both halves rather than letting either inherit the original element's edge transition onto the wrong side (the left half keeps the original's `transition_in`, since its start didn't move; the right half keeps the original's `transition_out`, since its end didn't move) — this is the same "shallow copy needs explicit per-field correctness" class of issue as invariant #22, just about which *side* a field belongs on rather than aliasing.
26. **Subtitle transcription is a second `MediaAnalysis` analyzer identity (`analysis.py`'s `ASR_ANALYZER = "whisper-asr"`, alongside the pre-existing `ANALYZER = "ffprobe"`) — not a new pipeline, model, or queue.** `enqueue_transcription`/`run_transcription` are siblings of `enqueue`/`run_analysis`, deduped the same way via the table's `(asset_id, analyzer, analyzer_version)` unique constraint, run by the same `media_analysis` Celery queue (`run_editor_transcription` task, same shape as `run_media_analysis`), and polled through the same `GET /v1/editor-operations/{man_...}` endpoint. **Credentials are resolved directly from `llm_providers`' enabled `kind="media"` endpoints that serve `audio_generation` (`analysis._resolve_asr_endpoint`), never through `app.agents.router`/`intent_router`** — that machinery exists to have an LLM pick among cost/latency-scored candidates for a user-initiated generation job; transcription is a deterministic analysis side-effect of an asset that already exists, with nothing to choose between and no job/credit-ledger semantics. Reusing the audio-generation endpoint's `base_url`/`api_key` is safe because AiHubMix-style gateways serve `/v1/audio/speech` (TTS) and `/v1/audio/transcriptions` (ASR) from the same account — `_call_asr` reuses `aihubmix_media.py`'s own `media_client_base`/`media_request_path` URL-joining helpers, not a new HTTP convention. **`GET /v1/editor-operations/{id}` gained its first real per-caller ownership check** (`man_` branch only, both the REST route and the MCP `editor.get_operation` dispatch) — every other branch (`exp_`/`epl_`) returns content whose id could only have been learned by already owning the row; a transcript is the first thing this endpoint exposes that's genuine user content keyed off an id alone, so don't copy the `man_` branch's ownership check pattern as if it were already established elsewhere in this same function — it isn't, and extending it to the other branches is out of scope for this invariant. **AI can trigger transcription (`editor.request_transcription` MCP tool, `editor:write` scope) but nothing can commit it without a human**: the tool only enqueues an analysis row and returns its id — there is no MCP tool, planner capability, or REST endpoint anywhere that turns a transcript into `insert_caption` commands automatically. That only ever happens through `front/src/features/editor/transcript-review-panel.tsx`, which requires a person to review (and can edit or exclude) each segment before the "insert as captions" button builds the batch — this is a deliberate, load-bearing gap in the tool surface, not a missing convenience feature to add later.
27. **Co-creation (`SeriesCollaborator`) is a management-tier permission grant, deliberately not a timeline-editor, trash, or publish/distribution grant — `_accessible_series`/`_accessible_episode` (`editor/service.py`) exist alongside `_owned_series`/`_owned_episode`/`_owned_cut`, and never replace or widen them.** An invite (`collaborators.invite`, owner-only, target resolved by `Profile.handle` **or** `User.email` via `_find_profile_by_identifier` — an "@" anywhere but the first character is treated as an email, otherwise as a handle — rate-limited via `series_collab_invite` — 10/300s) creates a `PENDING` `SeriesCollaborator` row; the invitee must `accept` (via a `series_collab_invited` notification) before `is_active_member` counts them, at which point they can view/edit the series' metadata, manage episodes (create/update/delete), write scripts (`/create/script`), manage content-links, and set the canonical work — exactly the surface routed through `_accessible_series`/`_accessible_episode` (`update_drama_series`, `create_episode`/`list_episodes`/`get_episode`/`update_episode`/`delete_episode`/`create_content_link`/`list_content_links`/`delete_content_link`/`set_canonical_work`, plus `script_writing.service`'s own `_owned_episode`). **`trash_drama_series`/`untrash_drama_series`/`purge_drama_series`, every timeline-editor entry point (`create_cut_from_job`/`acquire_lease`/`apply_commands`/exports/AI planning/cut revisions), and platform-connect/publish/analytics stay strictly `_owned_series`/`_owned_episode`/`_owned_cut` (owner-only)** — a collaborator can generate content and get billed for it (see below) but can never delete the project, enter the timeline editor, or touch distribution; this is a deliberate Phase-1 boundary, not an oversight to "finish" by widening those checks. `list_drama_series` (non-trash view only) is a union: `owner_user_id == user_id` **or** an active collaborator row exists — the trash view stays owner-only since a collaborator was never meant to see or manage the owner's deleted projects. **`GET /v1/drafts` follows the same live-seat rule:** `list_unpublished_work_drafts` omits a draft bound (`params.link_episode_id` or an `EpisodeContentLink`) to a series the caller neither owns nor actively collaborates on, so leaving (`SeriesCollaboratorStatus.REMOVED`) takes that production off 「最近生成记录」/作品集草稿 even though `Draft.user_id` is still the former collaborator (`GET /drafts/{id}` stays 200). **Credit billing is untouched by co-creation and needs no special-casing**: `credits_service.reserve` is always keyed off the *actual caller* (`GenerationJob.user_id`), never `Series.owner_user_id` — a collaborator generating content for a shared series is billed on their own `CreditAccount`, exactly like generating for their own series. `MAX_ACTIVE_COLLABORATORS_PER_SERIES = 20` counts `pending`+`active` rows together (so a pile of unanswered invites can't be used to dodge the cap) — a hardcoded module constant in `collaborators.py`, not a `zaolang-platform-config` entry, since it's low-churn; move it there if it ever needs to become tunable per-plan/per-user. A `(series_id, user_id)` pair only ever has one row (unique constraint) — re-inviting a `declined`/`removed` user resets that same row to `pending` rather than inserting a duplicate. `SeriesCollaboratorStatus.REMOVED` rows (and `DECLINED`) are kept, never hard-deleted, both for the unique-row-reuse behavior above and as an implicit audit trail. On the frontend the same boundary is driven by `DramaSeriesResponse.viewer_role` (`'owner' | 'collaborator'`): `dashboard-shell.tsx` shows a collaborator badge and hides trash/purge for shared cards, `series-detail.tsx` hides `SeriesAnalyticsOverview` and the trash dialogs for collaborators, `collaborators-panel.tsx` shows invite/remove only to the owner, and `episode-panel.tsx` fetches the parent series separately just to gate `PublishPanel`/`AnalyticsPanel` on `viewerRole !== 'collaborator'` — mirror the server rule in the UI, never widen it there.
28. **Script turns stream the model's reasoning as a separate `event: thinking` channel and persist it on the turn.** `scripts.py`'s SSE body interleaves `event: delta` (user-facing text) with `event: thinking` (`{"text"}` chunks of live reasoning — best-effort: some providers stream it token by token, others return it in one late burst) and the final `complete` frame carries the full `thinking` string, which is stored on `EpisodeScriptTurn.thinking_text` (migration `20260828_1056`). Because a first `delta` can be tens of seconds away, `_with_heartbeat` drains the producer on a background thread and emits a bare `: heartbeat` SSE comment every `_HEARTBEAT_INTERVAL_SECONDS` (12s) while nothing else is ready (this keeps a cold proxy buffer from looking like a hung connection; the real ceiling on a stuck call is `llm_client.STREAM_WALL_CLOCK_TIMEOUT_SECONDS`, enforced inside the stream loop) — a comment line has no `data:`, so `parseSseFrame` on the frontend drops it before it ever reaches `ScriptStreamEvent` handling (`test_scripts_streaming.py`). The frontend renders reasoning through the shared `LiveThinking`/`ThinkingDisclosure` components and `thinkingParagraphs` helper (`@/components/ai/*`, re-exported by `features/script/thinking-paragraphs.ts`) — don't build a script-specific thinking renderer; the same component serves the agent gateway's other thinking streams.
29. **A browser export is a leased job: it must be claimed, then heart-beaten every <45s, or Beat fails it.** `queue_exports` only creates `queued` rows (and reclaims stale ones first); `POST /v1/editor-exports:claim` (`exports.claim_next`, `capabilities.chrome_or_edge` required or `BrowserRequired`) hands the oldest queued export the caller owns to a `runner_instance_id` and stamps `lease_expires_at = now + 45s`; every `POST /v1/editor-exports/{id}/heartbeat` (`progress`, `stage ∈ encoding|uploading|verifying`) refreshes that lease and drives the status machine, and a terminal export can never be reopened by a heartbeat (`OperationTerminal`, `test_editor_plans_and_races.py`). `reclaim_stale_exports` (run by Beat's `expire_stale_editor_exports`, and inline at the top of `queue_exports`) fails any claimed/encoding/uploading row whose lease lapsed with `code="stale_lease"` — the encoded blob only ever lived in that browser tab, so there is nothing to resume; the user re-queues instead. `export-runner.ts` is the only claimant (`api.ts`'s `claimExport`/`heartbeatExport`); recovering an already-completed export back onto an episode is `ensure-bound-draft`, and dropping an unpublished one is `delete-export-dialog.tsx` → `DELETE /v1/editor-exports/{id}` (invariant #18).
30. **`POST /v1/episode-cuts/{cut_id}/edit-plans` is a streamed SSE response, not a JSON plan.** It answers `202` with `app.api.agent_sse.iter_agent_sse` frames from `editor_planner.stream_plan_timeline` — the same `event: thinking`/`delta`/`complete`/`error` shape as script turns (invariant #28) — where the `complete` frame carries the persisted `EditPlanResponse` built inside its own `session_scope()` (the request `DbSession` is closed by the time the generator runs — same rule as invariant #20). `FLAG_AI` and `_owned_cut` are checked *before* the stream opens, so a disabled flag is still a plain 404 rather than an in-stream error (`test_edit_plan_rest_checks_flag_before_calling_the_llm`). `apply`/`reject` on the resulting `plan_id` stay ordinary JSON, and `apply` still goes through revision CAS — a stale base revision is rejected, never merged.
31. **Timeline markers are document-level, not element-level, and capped.** `add_marker`/`remove_marker`/`update_marker` (`commands.py`, mirrored in `canonical.ts`) edit `document["markers"]` — `{id, at_ticks, label}` rows, `label` ≤ 120 chars, `MAX_MARKERS = 200`, client-supplied `marker_id` allowed but must be unique. Markers carry no rendering semantics (nothing in `compositor.ts` reads them; `timeline.tsx` draws them as bookmarks on the ruler) — they are human navigation/annotation only, and `editor_planner.py`'s prompt says so verbatim so the AI can place them but never expects them to affect output. Don't attach markers to tracks or elements, and don't let them grow into a second caption system.
32. **Trashing a series is a reversible status flip; purging is the real delete, and it is blocked while any episode remains.** `DELETE /v1/drama-series/{id}` → `trash_drama_series` sets `status=TRASHED` + `trashed_at` (`Conflict` if already trashed) and deliberately does not check episodes — the series just leaves the default list and shows in the `status=trashed` view; `POST .../untrash` reverses it. `DELETE .../purge` → `purge_drama_series` requires `TRASHED` first and 422s while `DramaEpisode` rows exist (`series_id` is `ondelete=RESTRICT`, so this is the domain layer stating what the DB would otherwise reject opaquely) — the user must delete each episode (invariant #18) before purging. All three are owner-only through `require_drama_series` (invariant #27), and the trash list view is owner-only too. Frontend: `trash-series-dialog.tsx`/`purge-series-dialog.tsx`, mounted from both `dashboard-shell.tsx` and `series-detail.tsx`; covered by `test_series_trash.py`.
33. **Edits apply locally first, then sync through one serial FIFO queue — the server is still the only source of truth.** `drama-editor.tsx`'s `apply(commands)` runs `canonical.ts`'s `applyBatch` against the current local document and renders that result immediately (a local validation error toasts and sends nothing); the batch is then pushed onto `queueRef` and `pump` submits one batch at a time, chaining `expected_revision_id` to the previous success. Only when the queue is empty does the server's document overwrite the local one, so a fast sequence of drags never flashes back to an older state. Any failure (including 409) empties the queue and goes through `recoverFromConflict → reload`, which re-adopts the server head wholesale — there is no client-side merge. `undo`/`redo`/`restore`/AI-plan-apply `await flush()` first so they act on a settled head. `disabled` means `readonly || !token` only; `busy` (a round-trip in flight) drives the header badge and `serverBusy` for export/history/plan, never a whole-tree `disabled`. To make this work, elements a batch *creates* get their ids on the client: `withPredictedIds` fills `element_id`/`track_id`/`marker_id`/`new_element_id`/`new_element_ids`, and `commands.py` accepts (and validates uniqueness of) those optional client-supplied ids on `insert_clip`/`insert_caption`/`add_track`/`add_marker`/`split_element`/`duplicate_elements` — a follow-up command in the same or a later batch can therefore reference an element the server hasn't confirmed yet. **Don't let the server mint ids the client didn't propose for these commands, and don't add a command that creates elements without the same optional-id field.** The `insert_clip` `asset_id` check is skipped locally (`knownAssets = new Set()`); the server remains the authority on asset ownership.
34. **`duplicate_elements {element_ids, delta_ticks?, new_element_ids?}` is the only copy primitive; `Ctrl+D`, `Ctrl+C`/`Ctrl+V`, and the AI planner all use it.** Each copy is a deep copy (`_deep_copy_element` / `deepCopyElement` — the same `effects`/`animations.channels`/transition treatment invariant #22 demands of split), gets a fresh id, and lands on its source's own track: at that track's end by default, or shifted by `delta_ticks` from the original when given. Paste is a duplicate with `delta_ticks = playhead − min(start_ticks)` of the clipboard (ids kept in the store's `clipboardIds`, not element snapshots — a pasted copy always reflects the element's *current* state, and a deleted source makes paste a no-op). `CutRevisionResponse.asset_meta` (`{asset_id: {duration_ticks, width, height, mime_type, media_type}}` — five fields, `RevisionAssetMeta` in `api/schemas/editor.py`; there is no `display_name`, read from `Asset` in `api/v1/editor.py`'s `_revision_assets`) is what lets the client build `ResolvedAsset`s without guessing `video/mp4` — trim-end clamps to `duration_ticks` and thumbnails use the real aspect. `PATCH /v1/episode-cuts/{cut_id}` (`name` only, `_owned_cut`, `FLAG_EDITOR`) backs the header's inline rename.
35. **An episode's roster thumbnail is auto-filled once and then belongs to the author.** `resolve_episode_preview_source` picks the video whose first frame becomes `DramaEpisode.preview_asset_id`, in a deliberate order: the canonical work's video, else a draft/work `EpisodeContentLink`, else a succeeded `EditorExport`, else the cut's `source_asset_id` — a short generated clip is preferred over a full export so ffmpeg never ingests a 256MB file to grab one frame. `maybe_fill_episode_preview` is wired into `create_content_link` / `set_canonical_work` / `create_cut_from_job` and **never overwrites** an existing preview; only `POST /v1/drama-episodes/{id}/preview:from-video` passes `overwrite=True`. `_try_fill_episode_preview` swallows its own failures — the write it rides along with must not fail because a frame could not be extracted. `PATCH /v1/drama-episodes/{id}` distinguishes bind from clear by `model_fields_set` presence, not by a null value, and `episodes_with_preview_source` is the batched read behind `has_preview_source` so the roster does not probe per row. Response side: `preview_asset_id` / `preview_url` / `has_preview_source`; the frontend is `features/drama-dashboard/episode-preview-thumb.tsx`. Upload purpose and sharing rules: `zaolang-media-assets`.
36. **A cut name is unique per episode+kind, and one job maps to one cut.** `create_cut_from_asset` traps `uq_episode_cuts_episode_kind_name` and raises `Conflict("该集已有同名剪辑。")` rather than letting the `IntegrityError` surface. `episode-cuts:from-job` is idempotent on the *job*: `_cut_for_source_job` returns the existing cut when the same job is submitted twice (in addition to the `_default_full_cut` reuse), so a double-click on 「进入剪辑」 does not fork a second timeline off one generation.
37. **Every export is labelled as AI-generated; only the visible label is the author's switch** (《人工智能生成合成内容标识办法》). `export-runner.ts` always writes the implicit label into the MP4 before `start()` (`aigcMetadataTags` → mediabunny `Output.setMetadataTags`: the standard `AIGC` JSON in the comment tag, `ContentProducer: zaolang`). The visible 「AI 生成」 pill is `ExportRenderOptions.aiLabel` — on by default in `export-panel.tsx`, drawn last by `composeFrame` (`aiLabelRect`: top-right, sized from frame height, never covered by another layer) and deliberately **not** part of `VariantSpec`, so it never changes a variant's hash or the backend's `caption_mode`. The preview does not draw it. `exports.complete_export` records an unsigned provenance manifest for the export asset (`media_service.record_provenance`, once per asset) — never claim C2PA signing (`zaolang-media-assets` invariant #7).
38. **The script lint suggests; it never blocks.** `app/domain/script_writing/lint.py` runs in code (no LLM) over the saved script for `GET /v1/scripts/{id}` → `lint`: runs of three same-size shots, directionless camera moves, camera blocks without a shot size, no-information words, emotion labels in action blocks, a named character inside a scene block, segments over the generation length or prompt budget (keyed `{heading}#{ordinal}` exactly as `script-breakpoint.ts` keys them), wide shots over dialogue in a vertical series (`is_vertical_delivery` from `Series.target_platforms_json`), and more than three speaking leads. Every vocabulary word also appears in the copywriter prompt text it enforces — `tests/unit/test_script_lint.py` fails if a prompt rule is reworded without the lint. Findings carry a format-skill `dimension` plus `suggested_skills` (`skill_library.format_skill_titles`). It must never insert or remove a breakpoint (that would shift every key and orphan bound drafts). The frontend shows it as `features/script/script-lint-panel.tsx`, collapsed, and only for the latest turn.
39. **Burned-in captions never run off the frame.** `compositor.ts::drawCaptions` lays captions out through the pure `engine/caption-layout.ts` (`layoutCaptionLines`): CJK breaks between characters and Latin only between words, closing punctuation never starts a line and opening brackets never end one, at most two lines (more only when several captions overlap in time — they are joined with `\n` and stack), shrinking through `FONT_SCALES` (down to 0.8×) before the last line is cut with 「…」. The single-line position (0.88h) is unchanged. Preview, export and the export precheck all draw through `composeFrame`, so they stay identical; layouts are cached per text/size/width because export redraws the same caption every frame.
40. **一键粗剪 writes its own cut and takes its order from the saved script.** `POST /v1/episode-cuts:assemble` (`editor_service.assemble_cut_from_script`, owner-only, `FLAG_EDITOR`) orders segments with `app/domain/script_writing/breakpoints.py` — a port of `script-breakpoint.ts` that must key `{heading}#{ordinal}` / trailing closer / `{heading}#L{blockIndex}` identically (`tests/unit/test_script_breakpoints.py` mirrors the frontend tests); the client's `ordered_keys` only narrows that list and never reorders it. Each segment's video is the owner's newest episode-linked draft for that key (`operation` empty, `text_to_video` or `image_to_video`): `Draft.output_asset_id`, else its latest `SUCCEEDED` job not hidden from history. Videos go end to end on `trk_video`; each dubbed line (`audio_generation` draft keyed `#L`) goes on `trk_audio` from its segment's start and never overlaps the previous line; every dialogue line becomes an `insert_caption`, timed to its voice clip or an estimated reading time. An asset with no `duration_ms` (`ticks_from_ms` would silently call it 1s), a missing output or an unowned asset is **skipped and reported** in `skipped[{key, reason}]`, not a failure; no placeable video at all is 422. It writes to the `kind=full`, name `粗剪` cut (get-or-create under `uq_episode_cuts_episode_kind_name`, row-locked) — never `主剪辑`, so the hand-edited timeline is untouched — as one revision parented on the current head. An active lease on 粗剪 is `LEASE_HELD` (409): close the editor first. Element ids are derived from track + script key, so a repeat click with unchanged outputs dedupes to the same revision by content hash — that, not an idempotency key, is what makes the button safe to double-click. The frontend entry is the 一键粗剪 button in `script-batch-toolbar.tsx` (`assembleCutFromScript` in `features/editor/from-job.ts`), which navigates to `/studio-editor/{cutId}`.
41. **The episode production board shows only what the data proves.** `features/drama-dashboard/production-board.tsx` (mounted in `episode-panel.tsx` between the script card and 生成的视频) is a stage track 剧本 → 角色 → 场景 → 分镜 → 配音 → 剪辑 → 成片 → 发布 plus a film strip, all computed by the pure `production-stages.ts` (tested in `production-stages.test.ts`) from what the panel already loads: the script, the episode-linked drafts (`indexBreakpointVideos`/`dubbedDialogueKeys`, same keys as the script studio), cuts, exports and `canonical_work_id`. A strip card's width is proportional to the draft's real `duration_ms`; a segment with no video is a fixed-width dashed 「未定时长」 frame — never an estimated length. A bound draft whose jobs all ended without a success is 生成失败, not 生成中; a video draft keyed to a segment the script no longer has is counted as 未匹配 instead of vanishing (scene renames, canvas invariant #13). Take counts and 「你在本集已花 / 可用」 come from each segment draft's own `GET /v1/generation-jobs?draft_id=` (only the viewer's jobs — collaborators are charged their own credits, invariant #27; spend counts `actual_credits` only, never a reservation) and `Me.available_credits`. It opens no stream of its own: it watches the notification center's newest item and refetches the one draft whose `payload.draft_id` it names.
42. **Audio gain is 0–200% end to end, fades are curves, and loudness is an export-time master.** `compositor.ts::layerVolumeAt` is the single resolver for a layer's gain (static `volume_millipercent` or the `volume` channel), bounded to `MAX_LAYER_VOLUME = 2` — the same 0–200 000 range `set_clip_volume`/`PROPERTY_RANGES` accept; never clamp it back to 1 (that silently dropped every boost). The export mix (`export-runner.ts::renderMixedAudio`) cuts segments at every volume keyframe and, for a keyframed clip, drives the gain with `setValueCurveAtTime(volumeCurve(...))` so a fade is a fade, not a step at the first keyframe; the preview mixer updates the same value every sync. **Ducking** (`engine/ducking.ts::buildDuckingCommands`, the 〰 button on an audio track header in `timeline.tsx`) is only ordinary `clear_keyframes` + `set_keyframe volume` commands on that track's clips — speech is every clip on the other unmuted audio tracks, merged across gaps shorter than fade-down + fade-up, ducked to 25% of the clip's own volume with a 0.2 s / 0.5 s fade — so it is undoable, syncs through the normal command FIFO, and respects the 64-keyframe channel and 100-command batch caps (truncating rather than failing). **Loudness** (`engine/loudness.ts`: BS.1770 K-weighting, 400 ms blocks, −70 LUFS absolute and −10 LU relative gates) is applied only to the finished export mix when `ExportRenderOptions.normalizeLoudness` is on (default on in `export-panel.tsx`): −14 LUFS, but never past a −1 dBFS sample peak. The preview plays the unnormalised mix — like the AI label, it's mastering, not timeline truth.
43. **Dubbing direction is closed and optional; a speaker's voice comes from their character card.** A dialogue block may carry `emotion` from the closed `copywriter.SCRIPT_EMOTIONS` (happy/sad/angry/fear/surprise/calm) — declared in `SCRIPT_JSON_SHAPE` and the dialogue rule of `_BLOCK_TYPE_RULES`, kept by `_sanitize_script`/`_sanitize_script_segment` only on dialogue and only when known (otherwise the key is omitted, so a plain line stays a 3-key block). A published `script_draft`/`script_revise` AgentSkill overrides those prompt constants, so it must be republished to ask for `emotion`. `batch-plan.ts::parseDialogueDirection` strips a leading 「（冷笑）」 direction from what TTS speaks and maps it onto the same set (a sneer/wry smile is never "happy"); the block's own `emotion` wins. The emotion travels as `extra.emotion` and is mapped per upstream in one place, `app/providers/tts_direction.py` — tts-pro gets its own `emotion` field only for happy/angry/fear/surprise, gpt-4o-mini-tts gets `instructions`, tts-1/-hd get nothing — and an unknown or missing value is never an error (GJ #14: default behaviour unchanged). A character's `preset_voice` (character library 「预设音色」) seeds the script batch dialog's per-speaker voice pickers (`BatchParams.voiceByCharacter`, speaker matched by `character_ref_id` then by name); `apply_character_refs(operation=audio_generation)` fills `extra.voice` from it only when the caller sent none, and never merges character reference *images* into an audio job (its one reference slot is a voice-clone sample).

## Product Path

Generation succeeds → "Enter editing" → `/studio-editor/{cutId}` → sequential export (the encode canvas uses the delivery variant's own width/height, even-pixel rounded for H.264; duration, resolution and estimated memory no longer refuse a queue) → `POST /v1/editor-exports/{id}/ensure-bound-draft` (reuses the unpublished source draft, or mints one with `params.link_episode_id` when none exists) or the explicit `POST /v1/drafts/{id}/bind-editor-export` → the eight-step publish flow. An episode's "最终成片" list recovers an unbound export with the same ensure-bound call, and drops an unpublished record with `DELETE /v1/editor-exports/{id}` (published binds stay).

Script writing is a separate, earlier path, and now the *only* way a `kind=drama` series gains an episode: `/create/short` (series library) → "新建短剧" or open an existing series → `/create/script?seriesId=` (or standalone `/create/script` — auto-creates its own series when no `seriesId` is given) → write an idea → streamed first draft → `/create/script/{episodeId}` → streamed revision turns, any turn's version browsable → back on `/create/short/episodes/{episodeId}`, each generated video (`EpisodeContentLink content_type in (draft, work)`) has a clickable poster to that clip's detail (`videoCreationStudioHref(draft.id)` for an unpublished draft, `/work/{id}` once published) and still offers "进入剪辑" (opens `studio-editor`, creating an `EpisodeCut` on first entry) or "直接发布" (the standard `/publish/{draftId}` form, or — once already published — the inline `PublishPanel`/`AnalyticsPanel`). "添加已有视频" attaches a finished standalone video-creation draft to this episode without minting a new series. Neither "open editor" nor "publish" is a stub any more; both are wired directly off the episode panel.
