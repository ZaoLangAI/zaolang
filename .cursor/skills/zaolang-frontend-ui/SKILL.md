# Consumer Frontend

## Scope

The current consumer routes under `front/src/app/[locale]/(site)/` and the component families they share. **Trust the actual `page.tsx` files, shared components, and visual e2e specs**, not a fixed page count from a doc — dark theme is the acceptance baseline.

## Invariants

1. **The access token lives only in memory.** Storing it in `localStorage` turns any XSS into permanent account takeover; the durable half is the httpOnly refresh cookie. On reload, every component that depends on auth state must tolerate the intermediate "no token yet, silently refreshing" moment.
2. **Refresh requests are coalesced**: `client.ts`'s `refreshInFlight` guarantees concurrent 401s trigger only one refresh. Don't implement your own retry inside a component.
3. **Protected actions go through the login wall + action recovery**: intercept → open `login-dialog` → on success, resume via `pendingAction`; on cancel, the action is **discarded**, never silently executed.
4. **Any endpoint that moves credits requires an `idempotencyKey`** (submitting a generation, purchasing credits).
5. **Every interactive component implements the full state set**: `default / hover / focus-visible / disabled / loading / error` (+ `selected`). Missing `focus-visible` gets caught by the accessibility suite.
6. **No UI component library** — that's how theme-token drift starts. Components consume semantic tokens only (see `zaolang-theming`); **never a hardcoded colour**.
7. **No horizontal overflow at any of the three breakpoints**: 1440×1024 / 1024 / 390×844, asserted as `scrollWidth === clientWidth`. The visual QA suite checks this page by page.
8. **All copy goes through next-intl** — hardcoded Chinese strings are never allowed (see `zaolang-i18n-region`).
9. **The command palette is a combobox, not a dialog**: `role="search"` container + `role="combobox"` input + `role="listbox"`/`role="option"`. This ARIA structure is checked by axe — read `e2e/a11y.spec.ts` before touching the markup.
10. **Video creation parameters must stay provider-safe**: H3's user controls only ever submit 4–15 seconds, ten aspect ratios (`16:9`/`9:16`/`1:1`/`4:3`/`3:4`/`21:9`/`3:2`/`2:3`/`9:21`/`adaptive`), `2K` or `768P`, an optional seed, and mutually exclusive normal-reference/first-last-frame modes. The legal set for each field is `aihubmix_media.py`'s per-model `NativeVideoModelProfile`, not a value hardcoded in the studio — a differently-profiled native video model (e.g. `wan2.7-videoedit`) has its own, narrower set and is hard-filtered out by the router if the studio submits something outside it. Create/new and short-form may still submit `2K`/`768P`. **A video remix path omits `video_options.resolution`** so the router does not treat a missing value as `2K` and hard-filter `wan2.7-videoedit`; if the user picks an aspect or resolution wan cannot honour, the router still drops it by profile. Uploads only ever pass a platform `Asset.id` — never a webhook, external URL, or arbitrary provider JSON inside `extra`. A video remix also puts the licensed source `current_version.output_asset_id` into `reference_asset_ids`.
11. **`/create/short/{cutId}` (the cut editor, moved from `/create/drama/{cutId}`) is a hard desktop Chrome/Edge gate.** Narrow screens get a notice only, never the timeline — don't reuse the studio's mobile bottom sheet here. This route is excluded from `a11y-mobile` scanning. A job page's "enter editing" link imports only `front/src/features/editor/from-job.ts` — never the `features/editor` barrel (that pulls WASM/mediabunny into the job page). `export-runner.ts` dynamically imports `mediabunny`. Details: `zaolang-editor-drama`.
12. **RSC list pages degrade gracefully when the API is unavailable — never a blank screen.** `serverFetchOrNull` / `adminFetchOrNull` collapse network failures and 5xxs into `null` (`ApiError.isUnavailable`). Discover, profile work lists, and admin statistics already follow this. The route-level fallback is `front/src/app/[locale]/error.tsx`.
13. **A `POST`-initiated SSE stream is a different shape from `use-job-stream.ts`'s GET feed, not a variant of it.** Shared reader: `lib/sse-post.ts` (`thinking` / `delta` / `complete` / `error`). Callers: script turns, prompt polish, edit-plan, admin debug-chat. The whole reply arrives on the body of the single request that started it, so there is no `Last-Event-ID`/reconnect/poll-fallback. Errors from a failed request must be parsed into an `ApiError` from the response body (mirroring `apiRequest`'s envelope handling) — throwing the raw response text shows the user a JSON blob instead of the backend's `error.message`. **Job GET streams treat `event_type === "thinking"` as live reasoning, not a stage:** do not write it into `STAGE_FOR_EVENT`, do not store it in `events`, do not touch `lastEventId` / `sequence` (an undefined sequence is `NaN` in `Math.max`). Show it with `components/ai/thinking-disclosure.tsx` (`aria-live="polite"`) under the current stage. Refresh does not replay in-flight thinking.
14. **`/create/short/{cutId}` (`FLAG_EDITOR`-gated, formerly `/create/drama/{cutId}`) and `/create/script` (`script_studio_enabled`-gated) are both feature-flag-gated, so neither is in the visual/a11y suites' page lists** — those lists (`e2e/visual.spec.ts`'s `PAGES`, `e2e/a11y.spec.ts`'s `PUBLIC_PAGES`) are deliberately public/anonymous-reachable pages only. Don't add a gated route there; it would either need seeded auth state or fail the sweep. `/create/short` itself (the drama-series dashboard: list series, drill into episodes, content-links, canonical work) is sign-in-gated only, not feature-flag-gated — see `zaolang-editor-drama` invariant #17 — and is already in both lists.
15. **The notification center has exactly one live source of truth**: `NotificationCenterProvider` is the only component that opens `use-notification-stream.ts`'s SSE connection (`GET /v1/notifications/stream`, backend-shared with the job stream's Redis pubsub — see `zaolang-generation-jobs`); the bell, the toast stack, and the full `/notifications` page all read from `useNotificationCenter()` / their own `GET /v1/notifications` fetch, never open a second stream. A right-side creation toast is keyed by `target_id` (not the notification `id`), because a job/export/script/draft-publish upserts one row across its whole lifecycle — keying by `id` would already dedupe correctly by construction, but keying by `target_id` explicitly is what makes "replace the card in place and push its timer back out" trivial to reason about (`notification-center-provider.tsx`'s `toasts` map). This toast is a separate surface from `components/ui/toast.tsx`'s bottom-center `ToastProvider`, and deliberately not deduped against it — an in-editor `export-panel.tsx` success/error toast and the same event's top-right creation toast can both be showing at once; that redundancy is intentional (the top-right one is the only one visible from anywhere else in the app) rather than a bug to fix by suppressing one. `CREATION_TARGET_TYPES` must stay aligned with the backend upsert targets (`generation_job` / `editor_export` / `episode_script` / `draft`).

16. **"Image Creation" is one card/operation with an asset-kind dimension layered on top, not three cards.** `ImageGenerationStudio` derives `image_to_image` from `text_to_image` the moment a reference image is attached (same pattern `VideoGenerationStudio` uses for `text_to_video → image_to_video`); the asset-kind picker is a second, independent axis on top of that (`general` / `character` / `scene` / `cover`), sets `assetKind`/`targetCharacterId`/`targetSceneId`/`autoAttachAsset` on the submit payload (see `zaolang-generation-jobs`), and is otherwise inert — don't reintroduce separate `text_to_image`/`image_to_image`/"edit" cards to express an asset-kind distinction that already lives in this picker. **`character` is a single option, not three** — a character's front/side/back turnaround views used to be three separate asset kinds (`character_front`/`_side`/`_back`); they are now one `ImageAssetKind.CHARACTER` plus an independent `CharacterViewAngle`, and the studio only ever submits it with the default (front). Generating the remaining view(s) is not a studio option at all — it's `character-library.tsx`'s per-cell "补全{view}" card button, which submits its own `image_to_image` job with `character_views` set to whichever of side/back that one cell is missing (not always both — see `missingReferenceViews`, `lib/characters.ts`) and polls it to completion (see `zaolang-generation-jobs` invariant on multi-output character jobs). This job's `prompt` is a fixed reference-only instruction (`CHARACTER_COMPLETION_PROMPT`, `lib/characters.ts`), never the character's own name/description — the backend (`execute_asset_planning`, see `zaolang-generation-jobs`) hard-overrides a side/back pass's intent to that same instruction regardless of what a caller sends, so this is belt-and-suspenders, not the only thing making it work. `ImageGenerationStudio`'s own "补全侧面/背面" button (`InlineImageResult`, right after a front view succeeds) is the one place this is still a single aggregate action rather than per-view — it also now requests only `missingReferenceViews(...)`, not an unconditional `['side', 'back']`, so re-clicking it after only one view was deleted doesn't silently overwrite the other, already-approved one. Don't add a per-view picker back into the studio form. **`ImageGenerationStudio` never fetches or renders style preset / system style ("画风库")** — that picker (`useStyleAndSkillPicker`) is used only by `VideoGenerationStudio` and `AudioGenerationStudio`. Don't add the gallery/preset half to the image shell to "keep parity" with video/audio; the removal was deliberate. Image (and video) prompts *do* apply template skills via `@` in `PromptField` (`useAppliedSkills`): only free or already-purchased skills whose `applicable_operations` include the current operation (empty means any); selecting one strips the in-progress `@query`, merges `prompt_suffix`/`aspect_ratio`, and submits `skill_ids`. Platform catalogue rows stay video-only, so a seed skill will not appear on the image `@` list. **The script studio's "生成角色图/场景图" jump-out is the one deep link into this picker from outside `/create/new` itself** — `ImageGenerationStudio`'s `initialAssetKind`/`initialTargetCharacterId`/`initialTargetSceneId`/`subjectNameHint`/`returnTo`/`returnLinkKind`/`returnLinkLabel` props (populated by `/create/new/page.tsx` from validated query params — `returnTo` is whitelisted to `/create/script/...`, never rendered from the raw string) exist only to pre-fill this same asset-kind/target state, not a second code path; on a terminal job, `InlineImageResult` shows a "返回文案创作" button back to `returnTo`, carrying `linkKind`/`linkLabel`/`linkRefId` (from `GenerationJobResponse.linked_character_id`/`linked_scene_id`, see `zaolang-generation-jobs` invariant #15) only for a succeeded job that actually linked something — a failed/cancelled job still gets the button, just without a `linkRefId` to auto-relink. This `returnTo`/`returnLinkKind`/`returnLinkLabel`/`linkRefId`/`subjectNameHint` naming is this project's first (and, for now, only) "jump out, do one thing, jump back with the result" deep-link convention — reuse these same names for a future case rather than inventing a parallel set.
17. **The generic "我的技能" tab (`collection` page's `skills` tab, `manage-skill-dialog.tsx`) never sees an `IMAGE_ASSET_SKILL_CATEGORIES` skill.** `skill_library_service.list_mine` excludes `character`/`scene_asset`/`cover_asset` by construction — that dialog's category dropdown and flat-params editing model can't represent a character/scene's structured `reference_assets`, and re-filing one into `scene`/`lens`/`style`/`other` there would silently corrupt it. Those three categories are maintained only from their own dedicated pages (`/create/characters`, `/create/scenes`) or, for a cover, the "另存为可分享技能" save dialog that both `job-progress.tsx` and `inline-image-result.tsx` carry their own copy of — never add them back to `CATEGORIES` in `manage-skill-dialog.tsx` or `create-skill-dialog.tsx`.
18. **Video creation has the same per-draft version history as image creation now — there is no more "material only" resume, and clips can auto-continue from each other's last frame.** `VideoGenerationStudio`'s `initialDraft`/`draftId` is a full resume, exactly like `ImageGenerationStudio`'s: every later submit reuses the same `draftId` (`GenerationSubmitInput.draftId`), and `GenerationVersionHistory` lists every job filed under it (see the table row above for its video-thumbnail rendering). `recent-draft-card.tsx`'s video 编辑 icon (`isVideoCreationOperation` + `videoCreationStudioHref`, `lib/video-draft.ts` — now the same shape as `lib/image-draft.ts`, no more "material" vs. "reopen" asymmetry) reopens the exact draft instead of seeding a brand-new `video_to_video` session; `create/new/page.tsx` resolves `?draftId=` into `initialDraft` for `operation === 'text_to_video'` the same way it already did for `text_to_image` (a `video_to_video`/`image_to_video` draft — remix, a raw material-editing entry — still has no independent "resume" shape of its own). One deliberate asymmetry survives on purpose: resuming does **not** auto-attach the resumed job's own output as the next submit's reference upload the way `ImageGenerationStudio`'s draft-resume effect does for `image_to_image` chaining — silently turning a plain prompt tweak into a `video_to_video` job on every resume would be a surprising default. `InlineVideoResult`'s explicit "基于此视频继续创作" button (`handleUseAsReference`, same shape as image's `handleUseAsReference` but never automatic) does that instead, only on click. Both studios still accept a `linkEpisodeId` prop, forwarded straight into `useGenerationSubmit`'s `submit()` call — see `zaolang-editor-drama` invariant #17 for what that does server-side. **New on the video side only**: `continuitySourceAssetId` (from `?continuityAssetId=`, only ever sent by the script studio's "建议切分"/"查看/调整视频" breakpoint chip when an earlier breakpoint already has a video — see `zaolang-editor-drama`'s `previousBoundVideoAssetId`) makes `VideoGenerationStudio` call `POST /v1/assets/{id}/frame {position:"last"}` once on mount, pre-filling the returned frame as `first_frame_asset_id` (`reference_mode: "frame_images"`) so consecutive script clips visually connect end to end; skipped entirely while `initialDraft` is set (a resumed session already has its own material), and removable via a small "取消衔接" affordance next to the params panel's continuity notice.
19. **Image and video creation never navigate to `/jobs/[jobId]`; audio still does.** `ImageGenerationStudio`/`VideoGenerationStudio` both pass `useGenerationSubmit` an `onSubmitted` callback (the two callers that do) instead of leaving it `undefined`, so a successful submit sets local `activeJobId`/`activeJobSeed` state and renders `InlineImageResult`/`InlineVideoResult` in `GenerationStudioShell`'s `previewSlot` instead of `router.push`-ing away — `AudioGenerationStudio` never passes this callback and keeps the original navigate-to-`/jobs/{id}` behavior unchanged. Every job filed under the same `Draft` (reused across "continue refining" submits via `GenerationSubmitInput.draftId`, resolved against `input.draftId` before falling back to `pendingDraft.current`) shows up in `generation-version-history.tsx`, which merges a fresh `GET /v1/generation-jobs?draft_id=` fetch with whichever job is currently streaming so the version currently generating is live without a second poller. Each studio's own "用作参考继续微调"/"基于此视频继续创作" re-fetches that version's output asset(s), **replaces** (not appends to, for the image side; video appends since it usually already has other references) `uploads`, and pre-fills the prompt from `GenerationJobResponse.prompt` — the same `draftId` carries forward, so this becomes the next version under the same draft rather than starting a new one. A draft resumed via `?draftId=` (`create/new/page.tsx`'s `initialDraft` prop, or the collection library's/script studio's draft cards and breakpoint chips, which link to `/create/new?mode={image,video}_creation&draftId={id}` instead of `/publish/{id}` — see `library-tabs.tsx`'s `draftResumeHref`) fetches `initialJobId ?? latest_job_id` once via `useResource` before seeding `useJobStream`, rather than starting the stream with a `null` initial job. This "always land back in the studio, never `/jobs/[jobId]`" rule extends to notification click-through too: `job_payload` (`zaolang-generation-jobs`) puts `draft_id` on every job notification's payload, and `notification-format.ts`'s `targetHref` routes there via the `{image,video}CreationStudioHref`/`is{Image,Video}CreationOperation` helpers (`lib/{image,video}-draft.ts`, shared with `draftResumeHref`) whenever the job's operation is an image- or video-creation one and a `draft_id` is present — otherwise (no draft, e.g. a sandbox-originated job, or an audio job) it still falls back to `/jobs/{id}`. **A notification href is `draftId` + `jobId`**; draft cards stay `draftId`-only and resume `latest_job_id`. Do not fold `returnTo` into either. The studio prefers `?jobId=` so a retry's queued/succeeded toast opens that attempt, not the first failed one (`submit()` also advances `Draft.latest_job_id` — see `zaolang-generation-jobs`). Same pathname `/create/new` + a query-only change does not remount a client studio, so `create/new/page.tsx` keys `CreateStudio` with `studioSessionKey` (`lib/studio-session.ts`): `draft:{id}|job:{jobId}` when a notification carries both, `draft:{id}` for a draft-card/breakpoint-chip resume, otherwise the script jump-out's `mode`/`assetKind`/`target*`/`subjectNameHint`/`linkBreakpointKey`/`continuitySourceAssetId` (the last two only matter for a "fresh", `draftId`-less session — two different unbound breakpoints must not share a key). Do not `router.replace` a `draftId` onto the URL after submit — that would change the key mid-stream and tear down the live job. The script jump-out's `returnTo`/`returnLinkKind`/`returnLinkLabel` trio (image-only — video's script jump-out is the breakpoint chip, which has nothing to jump back to) is written onto `Draft.params` (`return_to` / `return_link_kind` / `return_link_label`, via `draftReturnParams`) on first submit; when the URL has no trio, the page restores it from the fetched draft through `readDraftReturnContext` + the same `/create/script/` whitelist. A pre-existing draft without those keys still remounts onto the right session but has no "返回文案创作" button. "Never navigate to `/jobs/[jobId]`" cannot mean "never let the author answer a follow-up question" either — `inline-image-result.tsx`/`inline-video-result.tsx` render `job/awaiting-input-panel.tsx`'s `AwaitingInputPanel` in place whenever the active job (and, for image, the independent "补全侧面/背面" job) is `status === 'awaiting_input'`, the same component `job-progress.tsx` uses on the standalone page. This exists as defense in depth even though every image-asset-kind (`character`/`scene`/`cover`) graph now turns the generic `planning` node's clarify off entirely (see `zaolang-generation-jobs` invariant #21) — a `GENERAL` image or video job's plain `planning` node still has it on by default, so it can legitimately suspend.

## Extension Points

- **Add a page**: create a directory under `(site)/` (RSC renders server-side by default, fetching via `lib/api/server.ts`) → split interactive pieces into `'use client'` components → add trilingual copy to `src/i18n/messages/*.json` (all three files) → add it to the command palette's navigable items → add it to the visual and accessibility suites' page lists (`e2e/visual.spec.ts`, `e2e/a11y.spec.ts`) **unless it's flag-/sign-in-gated** (see invariant #14 — `/create/short/{cutId}` and `/create/script` are the existing exceptions).
- **Change discover filtering/sorting**: `TagFilter` / `DiscoverSort` write `q`/`tag`/`sort` via `Link`; the default `popular` is omitted from the query. The Hero is pinned to popular. Contract: `zaolang-discovery-search`.
- **Add a shared component**: place it in `components/ui/`, merge classes via `lib/cn.ts`, implement every state, keep it keyboard-reachable.
- **Modify the API client**: errors are always `ApiError` (carrying the backend error code) — never parse a response body inside a component.
- **Add a form**: use `components/ui/field.tsx`, mapping a backend 422's field paths to inline errors rather than a generic banner.
- **Add a notification type that should pop a toast**: giving it a `target_type` isn't enough — `notification-center-provider.tsx`'s `isCreationNotification` (from `notification-format.ts`) is an explicit allowlist (`generation_job` / `editor_export` / `episode_script` / `draft`) precisely because only those upsert one row per target on the backend (see `zaolang-generation-jobs`'s `sync_creation_notification`); anything else would stack a new toast per event instead of updating one in place. Add rendering (icon/copy) to `notification-format.ts` first regardless — the bell and the full list need it even if the toast stack doesn't. `POST /v1/drafts/{id}/publish` is 202: toast "submitted for review" and leave (`latest_job_id` → `/jobs/{id}`, else `/collection`). Do **not** `router.push(/work/{id})` — there is no `work_id` yet. Re-entering `/publish/{draftId}` shows a pending wait state or a rejected reason that can be edited and resubmitted.
