# Consumer Frontend

## Scope

The current consumer routes under `front/src/app/[locale]/(site)/` and the component families they share. **Trust the actual `page.tsx` files, shared components, and visual e2e specs**, not a fixed page count from a doc — dark theme is the acceptance baseline.

## Invariants

1. **The access token lives only in memory.** Storing it in `localStorage` turns any XSS into permanent account takeover; the durable half is the httpOnly refresh cookie. On reload, every component that depends on auth state must tolerate the intermediate "no token yet, silently refreshing" moment.
2. **Refresh requests are coalesced**: `client.ts`'s `refreshInFlight` guarantees concurrent 401s trigger only one refresh. Don't implement your own retry inside a component.
3. **Protected actions go through the login wall + action recovery**: intercept → open `login-dialog` → on success, resume via `pendingAction`; on cancel, the action is **discarded**, never silently executed.
4. **Any endpoint that moves credits requires an `idempotencyKey`** (submitting a generation, purchasing credits).
5. **Every interactive component implements the full state set**: `default / hover / focus-visible / disabled / loading / error` (+ `selected`). Missing `focus-visible` gets caught by the accessibility suite.
6. **No UI component library** — that's how theme-token drift starts. Components consume semantic tokens only (see `zaolang-theming`); **never a hardcoded colour**.
7. **No horizontal overflow at any of the three breakpoints**: 1440×1024 / 1024 / 390×844, asserted as `scrollWidth === clientWidth`. The visual QA suite checks this page by page.
8. **All copy goes through next-intl** — hardcoded Chinese strings are never allowed (see `zaolang-i18n-region`).
9. **The command palette is a combobox, not a dialog**: `role="search"` container + `role="combobox"` input + `role="listbox"`/`role="option"`. This ARIA structure is checked by axe — read `e2e/a11y.spec.ts` before touching the markup.
10. **Video creation parameters must stay provider-safe**: H3's user controls only ever submit 4–15 seconds, six aspect ratios, 2K, an optional seed, and mutually exclusive normal-reference/first-last-frame modes. Uploads only ever pass a platform `Asset.id` — never a webhook, external URL, or arbitrary provider JSON inside `extra`.
11. **`/create/short/{cutId}` (the cut editor, moved from `/create/drama/{cutId}`) is a hard desktop Chrome/Edge gate.** Narrow screens get a notice only, never the timeline — don't reuse the studio's mobile bottom sheet here. This route is excluded from `a11y-mobile` scanning. A job page's "enter editing" link imports only `front/src/features/editor/from-job.ts` — never the `features/editor` barrel (that pulls WASM/mediabunny into the job page). `export-runner.ts` dynamically imports `mediabunny`. Details: `zaolang-editor-drama`.
12. **RSC list pages degrade gracefully when the API is unavailable — never a blank screen.** `serverFetchOrNull` / `adminFetchOrNull` collapse network failures and 5xxs into `null` (`ApiError.isUnavailable`). Discover, profile work lists, and admin statistics already follow this. The route-level fallback is `front/src/app/[locale]/error.tsx`.
13. **A `POST`-initiated SSE stream is a different shape from `use-job-stream.ts`'s GET feed, not a variant of it.** `features/script/api.ts`'s `streamPost` reads a `fetch` response body the same low-level way (`ReadableStream` + manual frame parsing), but the whole reply — `delta` chunks, then one `complete` or `error` frame — arrives on the body of the single request that started it, so there is no `Last-Event-ID`/reconnect/poll-fallback protocol to implement. Errors from a failed request must be parsed into an `ApiError` from the response body (mirroring `apiRequest`'s envelope handling) — throwing the raw response text shows the user a JSON blob instead of the backend's `error.message`.
14. **`/create/short/{cutId}` (`FLAG_EDITOR`-gated, formerly `/create/drama/{cutId}`) and `/create/script` (`script_studio_enabled`-gated) are both feature-flag-gated, so neither is in the visual/a11y suites' page lists** — those lists (`e2e/visual.spec.ts`'s `PAGES`, `e2e/a11y.spec.ts`'s `PUBLIC_PAGES`) are deliberately public/anonymous-reachable pages only. Don't add a gated route there; it would either need seeded auth state or fail the sweep. `/create/short` itself (the drama-series dashboard: list series, drill into episodes, content-links, canonical work) is sign-in-gated only, not feature-flag-gated — see `zaolang-editor-drama` invariant #17 — and is already in both lists.
15. **The notification center has exactly one live source of truth**: `NotificationCenterProvider` is the only component that opens `use-notification-stream.ts`'s SSE connection (`GET /v1/notifications/stream`, backend-shared with the job stream's Redis pubsub — see `zaolang-generation-jobs`); the bell, the toast stack, and the full `/notifications` page all read from `useNotificationCenter()` / their own `GET /v1/notifications` fetch, never open a second stream. A right-side creation toast is keyed by `target_id` (not the notification `id`), because a job/export upserts one row across its whole lifecycle — keying by `id` would already dedupe correctly by construction, but keying by `target_id` explicitly is what makes "replace the card in place and push its timer back out" trivial to reason about (`notification-center-provider.tsx`'s `toasts` map). This toast is a separate surface from `components/ui/toast.tsx`'s bottom-center `ToastProvider`, and deliberately not deduped against it — an in-editor `export-panel.tsx` success/error toast and the same event's top-right creation toast can both be showing at once; that redundancy is intentional (the top-right one is the only one visible from anywhere else in the app) rather than a bug to fix by suppressing one.

16. **"Image Creation" is one card/operation with an asset-kind dimension layered on top, not three cards.** `ImageGenerationStudio` derives `image_to_image` from `text_to_image` the moment a reference image is attached (same pattern `VideoGenerationStudio` uses for `text_to_video → image_to_video`); the asset-kind picker is a second, independent axis on top of that (`general` / `character` / `scene` / `cover`), sets `assetKind`/`targetCharacterId`/`targetSceneId`/`autoAttachAsset` on the submit payload (see `zaolang-generation-jobs`), and is otherwise inert — don't reintroduce separate `text_to_image`/`image_to_image`/"edit" cards to express an asset-kind distinction that already lives in this picker. **`character` is a single option, not three** — a character's front/side/back turnaround views used to be three separate asset kinds (`character_front`/`_side`/`_back`); they are now one `ImageAssetKind.CHARACTER` plus an independent `CharacterViewAngle`, and the studio only ever submits it with the default (front). Generating the remaining view(s) is not a studio option at all — it's `character-library.tsx`'s per-cell "补全{view}" card button, which submits its own `image_to_image` job with `character_views` set to whichever of side/back that one cell is missing (not always both — see `missingReferenceViews`, `lib/characters.ts`) and polls it to completion (see `zaolang-generation-jobs` invariant on multi-output character jobs). This job's `prompt` is a fixed reference-only instruction (`CHARACTER_COMPLETION_PROMPT`, `lib/characters.ts`), never the character's own name/description — the backend (`execute_asset_planning`, see `zaolang-generation-jobs`) hard-overrides a side/back pass's intent to that same instruction regardless of what a caller sends, so this is belt-and-suspenders, not the only thing making it work. `ImageGenerationStudio`'s own "补全侧面/背面" button (`InlineImageResult`, right after a front view succeeds) is the one place this is still a single aggregate action rather than per-view — it also now requests only `missingReferenceViews(...)`, not an unconditional `['side', 'back']`, so re-clicking it after only one view was deleted doesn't silently overwrite the other, already-approved one. Don't add a per-view picker back into the studio form. **`ImageGenerationStudio` never fetches or renders style preset / creation skill / system style ("画风库")** — that picker (`useStyleAndSkillPicker`) is used only by `VideoGenerationStudio` and `AudioGenerationStudio`. Don't add it to the image shell to "keep parity" with video/audio; the removal was deliberate, not an oversight. **The script studio's "生成角色图/场景图" jump-out is the one deep link into this picker from outside `/create/new` itself** — `ImageGenerationStudio`'s `initialAssetKind`/`initialTargetCharacterId`/`initialTargetSceneId`/`subjectNameHint`/`returnTo`/`returnLinkKind`/`returnLinkLabel` props (populated by `/create/new/page.tsx` from validated query params — `returnTo` is whitelisted to `/create/script/...`, never rendered from the raw string) exist only to pre-fill this same asset-kind/target state, not a second code path; on a terminal job, `InlineImageResult` shows a "返回文案创作" button back to `returnTo`, carrying `linkKind`/`linkLabel`/`linkRefId` (from `GenerationJobResponse.linked_character_id`/`linked_scene_id`, see `zaolang-generation-jobs` invariant #15) only for a succeeded job that actually linked something — a failed/cancelled job still gets the button, just without a `linkRefId` to auto-relink. This `returnTo`/`returnLinkKind`/`returnLinkLabel`/`linkRefId`/`subjectNameHint` naming is this project's first (and, for now, only) "jump out, do one thing, jump back with the result" deep-link convention — reuse these same names for a future case rather than inventing a parallel set.
17. **The generic "我的技能" tab (`collection` page's `skills` tab, `manage-skill-dialog.tsx`) never sees an `IMAGE_ASSET_SKILL_CATEGORIES` skill.** `skill_library_service.list_mine` excludes `character`/`scene_asset`/`cover_asset` by construction — that dialog's category dropdown and flat-params editing model can't represent a character/scene's structured `reference_assets`, and re-filing one into `scene`/`lens`/`style`/`other` there would silently corrupt it. Those three categories are maintained only from their own dedicated pages (`/create/characters`, `/create/scenes`) or, for a cover, the "另存为可分享技能" save dialog that both `job-progress.tsx` and `inline-image-result.tsx` carry their own copy of — never add them back to `CATEGORIES` in `manage-skill-dialog.tsx` or `create-skill-dialog.tsx`.
18. **A resumed video draft is always a fresh `video_to_video` submission with the old output as material — never the same draft reopened.** This is the one deliberate asymmetry with `ImageGenerationStudio`'s `initialDraft` (invariant #19 below): the image side has real per-draft version history (`generation-version-history.tsx`) to iterate within, so resuming reuses `draftId`; the video side has none, so `VideoGenerationStudio`'s `initialDraft` prop only pre-fills `prompt`/`aspect`/`duration` from `initialDraft.params` and fetches `initialDraft.output_asset_id` into `uploads` as a `video_to_video` reference — the next submit creates a brand-new `Draft`, it never sends the old `draftId` back. `recent-draft-card.tsx` is the only entry point today (`isVideoCreationOperation` + `videoCreationStudioHref`, `lib/video-draft.ts` — the video-side sibling of `lib/image-draft.ts`, same shape, no shared code because the resume semantics genuinely differ), gated on the draft already having an `output_asset_id`; `create/new/page.tsx` resolves `?draftId=` into this prop only for `operation === 'text_to_video'` (a `video_to_video`/`image_to_video` draft has no independent "resume" shape of its own — it's already somebody's continuation). Both studios also accept a `linkEpisodeId` prop, forwarded straight into `useGenerationSubmit`'s `submit()` call — see `zaolang-editor-drama` invariant #17 for what that does server-side.
19. **Image creation never navigates to `/jobs/[jobId]`; video/audio always do.** `ImageGenerationStudio` passes `useGenerationSubmit` an `onSubmitted` callback (the hook's only caller that does) instead of leaving it `undefined`, so a successful submit sets local `activeJobId`/`activeJobSeed` state and renders `InlineImageResult` in `GenerationStudioShell`'s `previewSlot` instead of `router.push`-ing away — video/audio never pass this callback and keep the original navigate-to-`/jobs/{id}` behavior unchanged. Every job filed under the same `Draft` (reused across "continue refining" submits via `GenerationSubmitInput.draftId`, resolved against `input.draftId` before falling back to `pendingDraft.current`) shows up in `generation-version-history.tsx`, which merges a fresh `GET /v1/generation-jobs?draft_id=` fetch with whichever job is currently streaming so the version currently generating is live without a second poller. "用作参考继续微调" (`handleUseAsReference`) re-fetches that version's output asset(s), **replaces** (not appends to) `uploads`, and pre-fills the prompt from `GenerationJobResponse.prompt` — the same `draftId` carries forward, so this becomes the next version under the same draft rather than starting a new one. A draft resumed via `?draftId=` (`create/new/page.tsx`'s `initialDraft` prop, or the collection library's image-creation draft cards, which link to `/create/new?mode=image_creation&draftId={id}` instead of `/publish/{id}` — see `library-tabs.tsx`'s `draftResumeHref`) fetches its `latest_job_id` once via `useResource` before seeding `useJobStream`, rather than starting the stream with a `null` initial job. This "always land back in the studio, never `/jobs/[jobId]`" rule extends to notification click-through too: `job_payload` (`zaolang-generation-jobs`) puts `draft_id` on every job notification's payload, and `notification-format.ts`'s `targetHref` routes there via the same `imageCreationStudioHref`/`isImageCreationOperation` helpers (`lib/image-draft.ts`, shared with `draftResumeHref`) whenever the job's operation is an image-creation one and a `draft_id` is present — otherwise (no draft, e.g. a sandbox-originated job) it still falls back to `/jobs/{id}`. "Never navigate to `/jobs/[jobId]`" cannot mean "never let the author answer a follow-up question" either — `inline-image-result.tsx` renders `job/awaiting-input-panel.tsx`'s `AwaitingInputPanel` in place for both `job` and `completionJob` (the independent "补全侧面/背面" job) whenever either is `status === 'awaiting_input'`, the same component `job-progress.tsx` uses on the standalone page. This exists as defense in depth even though every image-asset-kind (`character`/`scene`/`cover`) graph now turns the generic `planning` node's clarify off entirely (see `zaolang-generation-jobs` invariant #21) — a `GENERAL` image job's plain `planning` node still has it on by default, so it can legitimately suspend.

## Extension Points

- **Add a page**: create a directory under `(site)/` (RSC renders server-side by default, fetching via `lib/api/server.ts`) → split interactive pieces into `'use client'` components → add trilingual copy to `src/i18n/messages/*.json` (all three files) → add it to the command palette's navigable items → add it to the visual and accessibility suites' page lists (`e2e/visual.spec.ts`, `e2e/a11y.spec.ts`) **unless it's flag-/sign-in-gated** (see invariant #14 — `/create/short/{cutId}` and `/create/script` are the existing exceptions).
- **Change discover filtering/sorting**: `TagFilter` / `DiscoverSort` write `q`/`tag`/`sort` via `Link`; the default `popular` is omitted from the query. The Hero is pinned to popular. Contract: `zaolang-discovery-search`.
- **Add a shared component**: place it in `components/ui/`, merge classes via `lib/cn.ts`, implement every state, keep it keyboard-reachable.
- **Modify the API client**: errors are always `ApiError` (carrying the backend error code) — never parse a response body inside a component.
- **Add a form**: use `components/ui/field.tsx`, mapping a backend 422's field paths to inline errors rather than a generic banner.
- **Add a notification type that should pop a toast**: giving it a `target_type` isn't enough — `notification-center-provider.tsx`'s `isCreationNotification` (from `notification-format.ts`) is an explicit allowlist (`generation_job` / `editor_export`) precisely because only those two upsert one row per target on the backend (see `zaolang-generation-jobs`'s `sync_creation_notification`); anything else would stack a new toast per event instead of updating one in place. Add rendering (icon/copy) to `notification-format.ts` first regardless — the bell and the full list need it even if the toast stack doesn't.
