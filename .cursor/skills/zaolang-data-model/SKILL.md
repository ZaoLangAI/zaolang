# Data Model & Migrations

## Scope

Schema is defined in exactly one place: `back/app/models/` is ground truth, and Alembic migrations are autogenerated from it. Any domain invariant expressible at the database layer (unique keys, checks, foreign keys) must be expressed there — don't rely on Python-only validation.

## Invariants

1. **IDs are always `new_id("<prefix>")`**: 48 bits of millisecond timestamp for index locality, 80 bits of randomness for non-enumerability. Never use an auto-increment integer or a bare UUID, and never hand-write an ID literal (except in tests).
2. **Amounts and credits are integers**, in the smallest unit (credits / minor unit). New amount columns use `Integer` — `Numeric`/`Float` are forbidden.
3. **Constraint names follow `NAMING_CONVENTION`**, or autogenerate produces repeated noisy diffs.
4. **The ledger's three unique keys must not be touched**: `CreditLedgerEntry`'s constraints on `(account_id, type, job_id)`, `idempotency_key`, and `payment_reference` are the database-level guarantees behind "a job can be captured at most once" and "a payment posts at most once." The Python-layer checks only give an earlier error.
5. **`JobEvent.sequence` is unique on `(job_id, sequence)` and increments from 1 with no gaps**: SSE reconnects replay events with `sequence > Last-Event-ID`; a gap or a duplicate makes the client miss events.
6. **Tombstoning keeps the row**: `LifecycleStatus.TOMBSTONED` only changes status — never `DELETE` a `Work` / `WorkVersion` / `LineageEdge`, or the lineage chain breaks. Deleting a user goes through anonymisation instead (see `zaolang-compliance-audit`).
7. **Enum values persist as strings.** Renaming one is a data migration; adding one is safe. A state-machine change must update `JOB_TRANSITIONS` at the same time.
8. **`Series` is one table with two kinds — never build a second episode table.** `cast` is the character roster (`/v1/series`); `drama` is a production project (`/v1/drama-series`, MCP `project_id`). Roster queries must filter `kind=cast`; a drama id against the roster API 404s. `Series` is excluded from `RESET_TABLES` (the roster survives resets); `make seed --reset` additionally runs `DELETE FROM series WHERE kind = 'drama'`, while editor sub-tables are in `RESET_TABLES`. Details: `zaolang-editor-drama`.
9. **A character or scene is a `CreationSkill`, not a row in its own table** — the old `characters` table was dropped by a data migration that converted every row into a draft/private `CreationSkillCategory.CHARACTER` skill and rewrote `Series.character_ids_json` and every `ScriptCharacter.character_ref_id` to point at the new skill id; a later migration did the same for the `scenes` table into `CreationSkillCategory.SCENE_ASSET` (historical `GenerationJob.request_json.character_ids`/`scene_ids` were deliberately **not** backfilled — completed job records are immutable history). Each's structured content (character: `voice_description` + `reference_assets: [{asset_id, view, label}]`; scene: just `reference_assets`) lives under a dedicated `params_json["character"]`/`params_json["scene"]` sub-key, kept separate from the `prompt`/`prompt_suffix`/`aspect_ratio` fields the `SCENE`/`LENS`/`STYLE`/`OTHER` template categories use that key for. A cover image (`CreationSkillCategory.COVER_ASSET`) is the third and simplest of these — no reusable roster, just the job's own output asset as `CreationSkill.cover_asset_id` with no dedicated `params_json` shape. All three are grouped as `IMAGE_ASSET_SKILL_CATEGORIES` (`app/models/enums.py`) and are always excluded from `skill_library_service.list_mine`/`list_public`'s default (template-only) view and from `execute_skill_context`'s generic `skill_ids` folding — see `zaolang-agent-gateway` and `zaolang-frontend-ui`.
10. **Mutating a nested list/dict inside a JSON/JSONB column in place is silently lost.** SQLAlchemy's change-tracking for `JSON`/`JSONB` columns compares the attribute's *identity*, not a deep diff — if a helper returns the same nested dict/list object that lives inside the ORM instance's loaded value and the caller mutates it in place (`payload["reference_assets"] = entries`), `session.flush()` can end up comparing that object to itself and conclude nothing changed, skipping the `UPDATE` entirely (seen first in `characters.service`/`scenes.service`'s reference-asset helpers). Always have accessor helpers return a **copy** of the nested structure (and each entry within it) before the caller mutates and reassigns it back to the column attribute. A regression test must call `session.expire_all()` (or refetch in a new session) before asserting — asserting against the same in-memory object the code just mutated proves nothing.

## Extension Points

**Add a table**

1. Add the class to the relevant `models/*.py`, inheriting `Base, TimestampMixin`, with `id` from prefixed `new_id`.
2. Export it from `back/app/models/__init__.py` — otherwise autogenerate can't see it.
3. `make migration m="add xxx"` → **open the generated migration and review it by hand** (autogenerate doesn't infer CHECKs, partial indexes, or `server_default`).
4. Verify with `make migrate` against an empty database — `make reset` is the cleanest check.
5. If it's a business table, add it to `back/app/scripts/seed.py`'s `RESET_TABLES`, or `make seed --reset` leaves stale data behind. A table that shares storage with `Series` but must keep some rows (like the roster) needs its own targeted `DELETE`, like the drama case — don't dump the whole `series` table into `RESET_TABLES`.

**Add a column**: nullable or with a `server_default` for a safe upgrade against existing data; a NOT NULL requirement means two steps (add nullable + backfill, then tighten). **Purely associative/traceability columns** (e.g. `JobEvent.node_id`, `AgentRun.node_id`, `AgentRun.input_json`, `GenerationJob.graph_override_json`, `SystemLog.job_id`) may be added as nullable, unbackfilled, and without a foreign key — like `AuditLog.target_id`, the referenced row is allowed to be cleaned up first while the log/trace record still needs to exist. These columns exist so admin can answer "who / which node," not to maintain referential integrity. `GenerationJob.origin` carries `server_default=user`, so existing rows are treated as consumer jobs.

**Add an enum value**: additive only, and check every `match` branch plus the frontend union type in `front/src/lib/api/types.ts`.

## Verify

```bash
make reset                      # empty database, migrated to head, plus seed data
cd back && conda run -n zaolang alembic upgrade head && conda run -n zaolang alembic check
make test-back                  # unique-key and invariant tests live under tests/unit/
make openapi                    # model changes usually change the schema — don't forget to commit frontend types
```
