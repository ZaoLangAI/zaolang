# Data Model & Migrations

## Scope

Schema is defined in exactly one place: `back/app/models/` is ground truth, and Alembic migrations are autogenerated from it. Any domain invariant expressible at the database layer (unique keys, checks, foreign keys) must be expressed there — don't rely on Python-only validation.

## Invariants

1. **IDs are always `new_id("<prefix>")`**: 48 bits of millisecond timestamp for index locality, 80 bits of randomness for non-enumerability. On a model this is `id: Mapped[str] = id_column("usr" | "wrk" | "job" | ...)` (`base.py`), whose column default calls `new_id(prefix)` and yields `f"{prefix}_{...}"` — so ids look like `usr_…`, `wrk_…`, `job_…`, `led_…`. Never use an auto-increment integer or a bare UUID, and never hand-write an ID literal (except in tests).
2. **Amounts and credits are integers**, in the smallest unit (credits / minor unit). New amount columns use `Integer` — `Numeric`/`Float` are forbidden.
3. **Constraint names follow `NAMING_CONVENTION`**, or autogenerate produces repeated noisy diffs.
4. **The ledger's three unique keys must not be touched**: `CreditLedgerEntry`'s constraints `uq_credit_ledger_job_type` on `(job_id, type)` (no `account_id` in the key), `uq_credit_ledger_idempotency` on `idempotency_key`, and `uq_credit_ledger_payment` on `payment_reference` are the database-level guarantees behind "a job can be captured at most once" and "a payment posts at most once." The Python-layer checks only give an earlier error.
5. **`JobEvent.sequence` is unique on `(job_id, sequence)` and increments from 1 with no gaps**: SSE reconnects replay events with `sequence > Last-Event-ID`; a gap or a duplicate makes the client miss events.
6. **Tombstoning keeps the row**: `LifecycleStatus.TOMBSTONE` (`"tombstone"`) only changes status — never `DELETE` a `Work` / `WorkVersion` / `LineageEdge`, or the lineage chain breaks. Deleting a user goes through anonymisation instead (see `zaolang-compliance-audit`).
7. **Enum values persist as strings.** Renaming one is a data migration; adding one is safe. A state-machine change must update the matching transition table at the same time — there are now two, `JOB_TRANSITIONS` and `CANVAS_AGENT_RUN_TRANSITIONS`; adding a status to one does not touch the other.
8. **`Series` is one table with two kinds — never build a second episode table.** `cast` used to be the character roster, exposed at `/v1/series`; that whole CRUD surface (`create_series`/`list_series`/`get_series_detail`/`add|remove_character_to_series`/`assign_episode` in `characters/service.py`, and the routes in `api/v1/characters.py`) was deleted together with the old single-clip `ShortformStudio` it only ever served — **there is no `/v1/series` route any more**, and no code path creates a new `kind=cast` row. The leftover `kind=cast` rows from before that deletion were purged by migration `ada14f32676f` (`20260829_1001_purge_orphaned_cast_series_rows.py`); the `kind` column itself was not dropped, and `delete_character` no longer scans rosters at all (it is now just `skill_library_service.delete` on the owned `CreationSkill` — see the module docstring in `characters/service.py`). `drama` is the one live kind now — a production project, exposed at `/v1/drama-series` (create/list/get/`PATCH` update), and also MCP's `project_id`. `Series` is still excluded from `RESET_TABLES`; `make seed --reset` additionally runs `DELETE FROM series WHERE kind = 'drama'`, while editor sub-tables (and `SeriesCollaborator`) are in `RESET_TABLES`. `DramaEpisode` routes (`api/v1/editor.py`, backed by `app.domain.editor.service`) split by scope: create and list mount under `/v1/drama-series/{series_id}/episodes`; per-episode get/`PATCH`/delete, `EpisodeContentLink` create/list/delete, `set-canonical-work`, cuts and exports mount under `/v1/drama-episodes/{episode_id}/...` — don't reintroduce a mount under `/v1/series/{id}/episodes`. `DramaEpisode.episode_kind` (an `EpisodeKind` enum — `main`/`trailer`/`teaser`/`bts`/`recap`/`other`) is the episode's own narrative-role field, unrelated to `Series.kind`; `season_number` (default `1`) plus `episode_number` are jointly unique per series (`uq_drama_episodes_series_season_number`). Details: `zaolang-editor-drama`.
9. **A character or scene is a `CreationSkill`, not a row in its own table** — the old `characters` table was dropped by a data migration that converted every row into a draft/private `CreationSkillCategory.CHARACTER` skill and rewrote `Series.character_ids_json` and every `ScriptCharacter.character_ref_id` to point at the new skill id; a later migration did the same for the `scenes` table into `CreationSkillCategory.SCENE_ASSET` (historical `GenerationJob.request_json.character_ids`/`scene_ids` were deliberately **not** backfilled — completed job records are immutable history). Each's structured content (character: `voice_description` + `reference_assets: [{asset_id, view, label}]`; scene: just `reference_assets`) lives under a dedicated `params_json["character"]`/`params_json["scene"]` sub-key, kept separate from the `prompt`/`prompt_suffix`/`aspect_ratio` fields the `SCENE`/`LENS`/`STYLE`/`OTHER` template categories use that key for. Because a character skill is now what a character *is*, its name carries a database-level uniqueness rule the old table used to imply: the partial unique index `uq_creation_skills_owner_character_title` on `(owner_user_id, title) WHERE category = 'character'` (`models/skill_library.py:69`, migration `b8c4e6a2d710`, which de-duplicates existing rows before creating it), enforced in the domain by `_require_unique_character_name` (`characters/service.py`) raising `ValidationFailed("角色名称已存在。")`. Scenes and covers have no such index. A cover image (`CreationSkillCategory.COVER_ASSET`) is the third and simplest of these — no reusable roster, just the job's own output asset as `CreationSkill.cover_asset_id` with no dedicated `params_json` shape. All three are grouped as `IMAGE_ASSET_SKILL_CATEGORIES` (`app/models/enums.py`) and are always excluded from `skill_library_service.list_mine`/`list_public`'s default (template-only) view. They are **no longer** skipped outright by `execute_skill_context`: an image-asset skill reached through `skill_ids` folds its *flat* keys only (`flat_template_params`), while every other skill folds through `foldable_params`, which strips `variables` — both helpers live in `back/app/domain/skill_library/folding.py` (`fold_params_prompt` moved there out of `nodes.py`) — see `zaolang-agent-gateway` and `zaolang-frontend-ui`.
10. **Mutating a nested list/dict inside a JSON/JSONB column in place is silently lost.** SQLAlchemy's change-tracking for `JSON`/`JSONB` columns compares the attribute's *identity*, not a deep diff — if a helper returns the same nested dict/list object that lives inside the ORM instance's loaded value and the caller mutates it in place (`payload["reference_assets"] = entries`), `session.flush()` can end up comparing that object to itself and conclude nothing changed, skipping the `UPDATE` entirely (seen first in `characters.service`/`scenes.service`'s reference-asset helpers). Always have accessor helpers return a **copy** of the nested structure (and each entry within it) before the caller mutates and reassigns it back to the column attribute. A regression test must call `session.expire_all()` (or refetch in a new session) before asserting — asserting against the same in-memory object the code just mutated proves nothing.
11. **`SeriesCollaborator` is a membership row, not a permission widener on the base `Series`/`DramaEpisode` ownership model.** It only ever grants management-tier access (view/edit series metadata, episode CRUD, script writing, content-links, canonical work) through the separate `_accessible_series`/`_accessible_episode` resolvers in `app.domain.editor.service` — the strict, owner-only `_owned_series`/`_owned_episode`/`_owned_cut` checks used by the timeline editor, trash/purge, and publish/distribution are untouched and never consult this table. `status` (`pending`/`active`/`declined`/`removed`) is a `SeriesCollaboratorStatus` string enum, additive-only like any other; only `active` counts toward `is_active_member`/`MAX_ACTIVE_COLLABORATORS_PER_SERIES = 20` (the constant lives in `domain/editor/collaborators.py`, not on the model). A `(series_id, user_id)` pair keeps exactly one row for its whole lifetime (the unique constraint) — re-inviting a `declined`/`removed` user resets that same row to `pending` rather than inserting a duplicate, so `declined`/`removed` rows are never deleted. Credit billing is unaffected: `credits_service.reserve` keys off `GenerationJob.user_id` (the actual caller), never `Series.owner_user_id`, so a collaborator's generation spend already lands on their own `CreditAccount` with zero special-casing. Details: `zaolang-editor-drama` invariant #27.
12. **A draft's applied version is a pointer, and hiding a version is a timestamp — never `DELETE` the job.** `Draft.applied_job_id` names the generation currently driving preview / publish / the recent-generations thumbnail (`output_asset_id` moves with it). `Draft.latest_job_id` still means "last submit" (retry and notification resume depend on it — do not fold the two). A successful settle writes both `output_asset_id` and `applied_job_id = this job`. `GenerationJob.draft_history_hidden_at` only drops the row from `GET /v1/generation-jobs?draft_id=`; the job, ledger, `JobEvent`s and assets stay. Details: `zaolang-generation-jobs` / `zaolang-api-contract`.

## Extension Points

**Add a table**

1. Add the class to the relevant `models/*.py`, inheriting `Base, TimestampMixin`, with `id` from prefixed `new_id`.
2. Export it from `back/app/models/__init__.py` — otherwise autogenerate can't see it.
3. `make migration m="add xxx"` → **open the generated migration and review it by hand** (autogenerate doesn't infer CHECKs, partial indexes, or `server_default`).
4. Verify with `make migrate` against an empty database — `make reset` is the cleanest check.
5. If it's a business table, add it to `back/app/scripts/seed.py`'s `RESET_TABLES`, or `make seed --reset` leaves stale data behind. A table that shares storage with `Series` but must keep some rows (like the roster) needs its own targeted `DELETE`, like the drama case — don't dump the whole `series` table into `RESET_TABLES`. The six canvas tables are the current exception to this step — none of them is in `RESET_TABLES`, so they are only cleared transitively by `TRUNCATE users CASCADE` / the drama `DELETE`; that is a gap, not a pattern to copy.

**Add a column**: nullable or with a `server_default` for a safe upgrade against existing data; a NOT NULL requirement means two steps (add nullable + backfill, then tighten). **Purely associative/traceability columns** (e.g. `JobEvent.node_id`, `AgentRun.node_id`, `AgentRun.input_json`, `GenerationJob.graph_override_json`, `SystemLog.job_id`) may be added as nullable, unbackfilled, and without a foreign key — like `AuditLog.target_id`, the referenced row is allowed to be cleaned up first while the log/trace record still needs to exist. These columns exist so admin can answer "who / which node," not to maintain referential integrity. `GenerationJob.origin` carries `server_default=user`, so existing rows are treated as consumer jobs.

**Add an enum value**: additive only, and check every `match` branch plus the frontend union type in `front/src/lib/api/types.ts`. `SeriesGenre` (`app/models/enums.py`, backing `Series.genre_tags_json`) is a recent instance of a purely additive dictionary enum — the frontend mirrors it as a plain string-literal array (`front/src/features/drama-dashboard/format.ts`'s `SERIES_GENRES`), not a generated union, so a new genre needs an entry there plus its `genre<PascalCase>` i18n key in all three locales, not a schema regeneration.

## Verify

```bash
make reset                      # empty database, migrated to head, plus seed data
cd back && conda run -n zaolang alembic upgrade head && conda run -n zaolang alembic check
make test-back                  # unique-key and invariant tests live under tests/unit/
make openapi                    # model changes usually change the schema — don't forget to commit frontend types
```
