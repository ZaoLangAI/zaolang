# Generation Jobs & Queues

## Scope

Turn a generation request into a job that's trackable, replayable, and settleable. The state machine and event stream are the **client's single source of progress truth** — don't keep a second copy of progress anywhere else.

Two surfaces submit jobs, not one: `api/v1/jobs.py` (the studios) and the canvas Agent (`domain/canvas/agent_service.py`, see `zaolang-canvas`). Both go through `jobs_service.submit` and `dispatch.enqueue_or_fail`, and both settle through the same state machine — a change to submission, enqueue or settlement has to hold for both.

## Invariants

1. **Status transitions only go through `state_machine.transition`**, which lands via a conditional UPDATE with `WHERE status IN (...)`. Legal edges are defined in `JOB_TRANSITIONS`, and **terminal states have no outgoing edges**: any transition attempted after `succeeded/failed/cancelled/expired` must raise `InvalidJobTransition`. This is exactly what blocks out-of-order or redelivered provider callbacks.
2. **Exactly one terminal state wins**: if two callbacks arrive at once, only one succeeds — the loser errors rather than overwriting the result.
3. **`JobEvent.sequence` increments from 1 with no gaps or duplicates.** SSE reconnects replay from the database using `Last-Event-ID`, then switch to the live Redis pubsub stream; a gap stalls the client, a duplicate gets skipped. **Thinking tokens are not JobEvent rows.** `nodes.publish_thinking` only `publisher.publish_job_event`s a Redis frame (`event_type=thinking`, incremental `thinking`, no `sequence`). Consumer and admin SSE forward those via `_sse_live` (a `data:` frame with no `id:`), and must not advance `last_sequence`. Reconnect backfill still only reads `JobEvent`; in-flight thinking is lost on refresh, same as a script-writing turn dropping `create-stream-store`. Never invent a fake `sequence` for a thinking frame — C-end merge, iOS `applyStreamEvent`, and SSE `Last-Event-ID` would treat it as a stage event. `public_message` stays a user-friendly stage sentence; do not write reasoning text into it.
4. **Reaching a terminal state must write `finished_at`** and must complete credit settlement: success calls `settle_success` (capturing actual usage), everything else calls `settle_release` (releasing the reservation). **A terminal state without settlement is a dangling reservation**, and it shows up in admin alerts. **Exception: product sandbox runs (`origin=sandbox`)** still go through the state machine and get `finished_at`, but `settle_*` is a no-op (no `reserve` / `capture` / `release`) — `quoted_credits` only records "what it would have cost."
5. **Cancellation is a request, not a command**: outside `CANCELLABLE_JOB_STATUSES` a job can't be cancelled; a job already submitted to a provider may still complete and be billed, settled against the provider's actual result. `POST .../cancel` only stamps `cancel_requested_at` (`sm.request_cancel`); if `cancellation.should_honor_immediately` says nothing is mid-flight inside a worker (`CREATED`, `AWAITING_INPUT`, or `RUNNING`/`SUBMITTED` parked on an `AsyncProviderTask` checkpoint) the same request settles it via `honor_user_cancel`, otherwise it emits `ack_cancel_request` and the runner honors it at the next node boundary. A user can still click cancel while a job is suspended waiting on an external task, so every time `poll_once()` claims a task it first checks `cancel_requested_at`; a hit runs `async_polling._cancel()` = `async_tasks.cancel_upstream` (provider `cancel()`, close the `ProviderAttempt`, settle the task) then `honor_user_cancel` (`settle_release` + transition to `CANCELLED` + the `CANCELLED` event) without resuming the workflow — the same semantics as the cancellation check inside `execute_provider_generate`. The admin `admin/jobs.py::terminate()` also synchronously calls `async_tasks.cancel_upstream()` within the same request when it hits an in-flight `AsyncProviderTask` — it's no longer "change status only, don't notify the provider." A missing catalogue capability or a failing `provider.cancel()` doesn't block the status transition either way — it just logs a `system_log.emit(level=warning/error, ...)`.
6. **`created` can also transition to `expired`**: if the broker goes down, a job may never get picked up — without this edge, its reservation would be stuck forever.
7. **The submission endpoint must be idempotent** (`Idempotency-Key`), or a double-click reserves credits twice.
8. **Quoting and reservation happen inside the submission transaction**: `quote_for` first, then `reserve` (both inside `jobs_service.submit()`); the enqueue happens *after* `session.commit()`, via `domain/jobs/dispatch.py::enqueue_or_fail` → `tasks.dispatch_generation`, so a broker outage can't roll back the reservation — `enqueue_or_fail` instead transitions the job to `FAILED`, calls `settle_release(reason="enqueue_failed")`, writes an `ENQUEUE_FAILED` event and raises, rather than leaving the reservation for `expire_stale_jobs` to notice ~30 minutes later. **Both submitting surfaces must use it** — `api/v1/jobs.py::_enqueue_or_fail` is now only a delegating wrapper kept so tests can monkeypatch the name, and the canvas Agent calls `dispatch.enqueue_or_fail` directly; a third surface that hand-rolls `tasks.dispatch_generation` would strand reservations the others release. Sandbox submissions still call `quote_for` but skip the balance check and `reserve`, leaving `reserved_credits=0`.
9. **`RUNNING` can span multiple Celery task boundaries.** An async provider (AiHubMix video, and `dmxapi_media`'s video models too — this is not AiHubMix-only) returns `pending=True` once its remote task is created; `WorkflowRunner` writes an `AsyncProviderTask` checkpoint and returns immediately, leaving the job `RUNNING` — **this is not a terminal state, cannot settle, and cannot transition** while a Beat periodic task drives the rest via polling. Whether a job is stuck is judged by `AsyncProviderTask.deadline_at`, not "how long since a worker touched it."
10. **An in-flight task can be claimed by only one Beat tick at a time**: `claim_due` uses a conditional UPDATE to win `claimed_at` (the same pattern as `state_machine.transition`); losing the race means skipping. Without this, two ticks would resume the same workflow twice, producing two results and two settlements.
11. **H3 polling makes exactly one query per tick, 15 seconds apart.** A terminal state that still carries `output` gets downloaded and marked `partial_output` before entering the existing Quality node — deliverability is a quality-check decision, not something to discard just because the provider reported failure. New checkpoints store typed references, but resuming still accepts the older `reference_object_keys` shape.
12. **Worker and Beat must both stay running at all times.** Worker consumes generation queues; Beat is solely responsible for dispatching periodic tasks like `poll_async_provider_tasks` and `expire_stale_jobs` on schedule. With Worker but no Beat, external tasks never get polled and stuck jobs never release their reservations. Video/audio entry points share undecorated execution functions — a `bind=True` Celery Task must never call another bound task directly.
13. **`JobEvent.node_id` records which graph node actually wrote the event** — it's not inferred from `event_type`. A `custom_agent` node always emits `JobEventType.PROGRESS`, and so do async-polling heartbeats and quality retries — the same event type can map to several different nodes in the graph. `WorkflowRunner._execute_node` sets `ctx.state["_current_node_id"]` to the current node before calling the executor; both `nodes.py::_emit` and `async_polling.py::_emit` (the latter using the already-known `task.node_id`, never guessing) pass it into `append_event(node_id=...)`. A blank `node_id` only happens on historical events written before this migration — the frontend falls back to matching by `event_type`, which doesn't excuse new code from filling it in.
14. **`GenerationParams`' asset-kind fields are additive and default to today's behavior.** `asset_kind` defaults to `ImageAssetKind.GENERAL` (a pure free-form text-to-image/image-to-image job — the `asset_planning`/`asset_output_advance`/`asset_output_link` nodes are no-ops for it, since the graph for `GENERAL` is the original `default_graph`, not `asset_graph`); `target_character_id`/`target_scene_id` select which character skill (`CreationSkillCategory.CHARACTER`) / scene skill (`CreationSkillCategory.SCENE_ASSET`) to write the output back into — omitted for either kind auto-creates a fresh draft skill instead (`AssetOutputLinkConfig.auto_create_character`/`auto_create_scene`, both default `True`; the two kinds have been at parity since the script studio's "生成角色图/场景图" jump-out needed scene auto-create too — there is no longer a "scenes just leave the output unattached" special case). `subject_name_hint` (`max_length=60`) overrides the planner's own guessed `subject_name` when auto-creating — only a caller that already knows the exact name should send it (the script studio passes the script's own character name/scene heading); it's ignored once a target id is set, since there's nothing to name. `auto_attach_asset` (default `True`) is the client's opt-out — set to `False` to borrow an existing character's front-view reference for side/back consistency (still merged into `reference_asset_ids` by `characters_service.apply_character_refs`) without also writing the new output back into that character's roster. `character_views` (a list of `CharacterViewAngle`, `max_length=3`, only valid with `asset_kind == CHARACTER`) names which view(s) this one job produces; a `model_validator` canonicalizes it into front→side→back order regardless of the order the client sent, and an unset value means `[FRONT]` — a plain single-view request. All fields here are ignored by every non-image operation.
15. **`execute_asset_output_link` writing back to a character or scene skill is the *only* place a successful generation mutates something outside `GenerationJob`/`Work`/`Draft`.** It runs after `asset_output_advance`'s `done` port and before `settle_success`, is a no-op under `dry_run` or when `asset_kind` is `GENERAL`/`auto_attach_asset=False`/nothing recorded, and iterates every entry `asset_output_advance` appended to `ASSET_OUTPUTS_STATE_KEY` (one per produced view) — for the character path, the *first* iteration either appends to an existing character skill's `params_json["character"]["reference_assets"]` or creates a fresh draft one, and every subsequent iteration in the same job reuses that same character id rather than creating a second one; the scene path (single output only, no multi-view looping) works the same way against `params_json["scene"]["reference_assets"]`, including the same auto-create-when-no-target branch. On the video axis, only `VideoAssetKind.CHARACTER_ACTION` attaches: `_link_character_action_output` calls `characters_service.append_action_clip` (writing `params_json["character"]["action_clips"]`, *never* `reference_assets` — `apply_character_refs` would otherwise feed the clip into a future image job's `reference_asset_ids` as if it were a still) and may set `linked_character_id`; `transition_video` / `cover_video` (like image `COVER`) have no library to attach to and stay plain generated assets. Whichever character/scene id actually got used (the target the client passed, or the one just auto-created) is also written onto `GenerationJob.linked_character_id`/`linked_scene_id` (nullable `String(40)`, not FK-checked, at most one ever set) and exposed on `GenerationJobResponse` — the script studio's "返回文案创作" jump-back reads this to auto-relink the script entry without the user re-picking from `ScriptLinkPicker`. See `zaolang-data-model` invariants #9 (the `CreationSkillCategory.CHARACTER`/`SCENE_ASSET` storage shape) and #10 (helper functions here must return **copies** of nested `params_json`/`reference_assets_json` entries before mutating, or SQLAlchemy's flush silently skips the `UPDATE`).
16. **The product sandbox is a real job, not a `dry_run`.** `POST /v1/admin/workflow-templates/{operation}/sandbox-run` creates a `GenerationJob(origin=sandbox)` that runs the same Celery pipeline, JobEvent stream, SSE, quality checks, and asset registration — it only skips the credit ledger, consumer lists/notifications, and Draft/Work. Planning/`copy_generate` follow-ups behave like the consumer path: entering `AWAITING_INPUT`, presented and resumed via `GET/POST /v1/admin/jobs/{id}/input-request|answer` (the consumer route `/generation-jobs/{id}/input-request` still 404s for sandbox jobs). `graph_override_json` lets an unpublished draft graph run a trial without writing back to `workflow_template_id`. `WorkflowContext.dry_run` stays reserved for unit tests that walk the graph without persisting. A successful sandbox output additionally enters `POST_GENERATION` moderation (`reason_code=SANDBOX_OUTPUT`); a Safety `NEEDS_REVIEW` still enters `PRE_GENERATION`.
17. **`text_to_image`/`image_to_image` resolve to one shared workflow-template family, not two.** `jobs_service.submit()` always calls `workflow_templates_service.get_active(session, operation, asset_kind)` with the job's *actual* operation, but `get_active`/`list_versions`/`publish` all canonicalize `image_to_image` onto `text_to_image` first (`workflow_templates_service.canonical_operation`) — a job submitted as either operation for the same `asset_kind` is pinned to the identical `workflow_template_id`. The same helper also merges `image_to_video`/`video_to_video` onto `text_to_video`, so the three video operations share one template family per `VideoAssetKind` (`VIDEO_ASSET_OPERATIONS`); every other operation is returned unchanged. This is deliberate: the prompt is mandatory and an attached reference image is only extra input, not a different pipeline, so there is exactly one graph to configure per `asset_kind` regardless of which operation a given job happened to be. `GenerationJob.operation`/pricing still record the real operation; only template *storage and resolution* are merged. **A reference image is optional for `image_to_image` too** — `validate_generation_params` (`api/schemas/jobs.py`) does not require one (unlike `image_to_video`), `nodes._REFERENCE_REQUIRED` (the sandbox live-generate gate) excludes it, and `aihubmix_media._submit_image` already only attaches `image` to the provider body when a reference happens to be present. The frontend still only ever derives `operation='image_to_image'` the moment a reference is attached (`image-generation-studio.tsx` / `video-generation-studio.tsx` — the single `generation-studio.tsx` this used to name was split in two), but a bare API/sandbox call with `operation=image_to_image` and no reference is a legal, supported text-to-image-shaped request — don't reintroduce a mandatory-reference check for it.
19. **`GenerationJob.draft_id` is what turns "continue refining" into a version history, not a new model.** Both the image and video studios reuse the same `draft_id` across every submit of the same creative idea (`GenerationSubmitInput.draftId`, `use-generation-submit.ts`) instead of creating a fresh `Draft` each time — this was image-only at first, but `VideoGenerationStudio` grew the identical `draftId`/`GenerationVersionHistory` architecture (see `zaolang-frontend-ui` invariant #18/#19), so nothing about this mechanism is image-specific on the backend or in `use-generation-submit.ts`. `GET /v1/generation-jobs?draft_id=` (see the `jobs.py` row above) is the only new read this needed — it excludes `draft_history_hidden_at IS NOT NULL` and uses `limit=50` so a long refine chain is not truncated at the generic list default of 20. There is deliberately no branching/tree structure — every job under a draft is just one flat, chronological list (`generation-version-history.tsx`), and "branching" from an older version is expressed by resubmitting with that version's output as the new reference and prompt, still against the same `draft_id`, not by a parent/child column on `GenerationJob`. **`latest_job_id` and `applied_job_id` are different pointers.** Submit / retry / promote still only advance `Draft.latest_job_id` (`_point_draft_at_job`). A successful settle writes `output_asset_id` **and** `applied_job_id = this job` (a new success becomes current until the author pins an older one) — **unless the draft is already pinned to a job created later than this one**, in which case both writes are skipped, so a slow older job landing after a newer one can't silently clobber the newer pin. `POST /v1/drafts/{id}/applied-version` `{job_id}` re-pins a succeeded, unhidden job with output without moving `latest_job_id`. `DELETE /v1/drafts/{id}/versions/{job_id}` stamps `draft_history_hidden_at` (in-flight is 422); if that job was applied, the next still-visible succeeded job takes over, else both pointers clear. Never hard-delete the job — ledger / events / assets stay. This is a distinct, unpublished-draft-scoped concept from the lineage graph (`zaolang-lineage-graph`), which only exists between published `Work`s. `back/app/domain/notifications/push.py`'s `job_payload` also copies `draft_id` onto a job notification's `payload` when present — that's how `notification-format.ts`'s `targetHref` (`zaolang-frontend-ui` invariant #19) can send an image-creation job's notification back into the studio instead of `/jobs/[jobId]`.
20. **One `GenerationJob` can carry multiple outputs, but only for `asset_kind == CHARACTER` with more than one `character_views` entry.** `GenerationJob.output_asset_ids_json` (nullable `JSONB`, alongside the pre-existing single `output_asset_id`) and `PipelineOutcome.asset_ids` carry the *list* form; `GenerationJobResponse.output_asset_ids`/`output_urls` expose it over the API, additively — every other operation/asset-kind still only ever populates the singular fields. `asset_output_advance` is what drives this: after each `quality_check` pass it appends the just-produced asset to `ASSET_OUTPUTS_STATE_KEY`, and if `character_views` names a view not yet produced it resets `ctx.prompt` and loops back to `asset_planning` (`retry`-kind edge, `next` port) rather than falling through to `asset_output_link`/`settle_success` — so a 3-view character job runs `asset_planning`→...→`asset_output_advance` three times before ever reaching settlement. `credits.pricing.quote()`'s `output_count` parameter (from `jobs_service.character_output_count`, `len(character_views)` or `1`) multiplies both the base price and `estimated_seconds` accordingly — a 3-view job is priced and quoted as 3x, not 1x with two "free" extra views.
21. **The generic `planning` node's clarify slot defaults to on (`PlanningConfig.allow_followup_question = True`), but every image-asset-kind graph explicitly turns it off.** `execute_planning`'s `planner.clarify()` call has no `asset_kind`/`character_view` context at all — the dedicated `asset_planning` node right after it in the same graph is what actually has that context (invariant #14 above) — so left at the default, clarify can misjudge a completion-job's fixed, deliberately terse prompt (API/iOS `completeViews` still send — and `execute_asset_planning` unconditionally overrides a side/back pass's intent to regardless, see the `nodes.py` row above — the fixed reference-only, per-view instruction "参考本图生成侧面图"/"参考本图生成背面图", not a character's name/description) as missing scene/action/shot info and ask for exactly what a character/scene/cover asset must NOT have (`planner._ASSET_KIND_BRIEF`), suspending the job at `AWAITING_INPUT` with nothing for `asset_planning` to ever act on. A Web `character` front job is a sheet, not a completion, but the same clarify-off rule still applies. `defaults.py::_build_graph` therefore seeds `planning.config.allow_followup_question = False` whenever `with_asset_nodes=True` (i.e. every `asset_graph` call — image `character`/`scene`/`cover` and video `scene_video`/`character_action`/`transition_video`/`cover_video`); `video_analysis_graph` hardcodes the same `False` (its `prompt` is only an optional note, never worth pausing the job over); the plain `default_graph` (`GENERAL` on either axis, and every other operation) keeps the default on, since a plain text-to-image job can legitimately be underspecified. **Changing this default in `defaults.py` only affects graphs seeded from here on** — `ensure_default_templates` never re-seeds a bucket that already has an active template, so every already-published `(operation, asset_kind)` row needs its own one-time data migration to patch `graph_json` in place (see `back/alembic/versions/20260818_2000_disable_asset_planning_followup.py`: read every active, asset-kind-scoped row, flip the `planning` node's `config.allow_followup_question`, write the row back directly — no new template version, since these rows are auto-seeded, not an operator's hand-edited history). A job that already suspended at `AWAITING_INPUT` before such a migration runs also doesn't self-heal — it has to be answered or cancelled (`honor_user_cancel`) explicitly; the migration only stops new occurrences. **This same context-blindness also poisoned the *main* `planner.plan()` call, not just its clarify sub-step** — `nodes._plan_enhancements` (read by `execute_provider_generate` on every pass) used to unconditionally fold `ctx.state["plan"]["prompt_enhancements"]`/`negative_prompt_suggestions` into the request regardless of asset kind, and that plan runs exactly **once**, *before* a multi-view `CHARACTER` job's per-view loop (invariant #20) even starts — a real dev-DB `agent_runs` row for a `character_views: ["side","back"]` completion job shows the generic plan's own enhancements literally reading "侧面图展示...背面图展示..." (both views, one shot), which then got re-applied to *both* the side pass's and the back pass's request, each leaking the other view's description in; for a bare-name intent it also fabricated its own from-text-only physical description (e.g. "中年女性，短发…") that competed with the real attached reference photo during image-to-image. `_plan_enhancements` now returns `(ctx.prompt, ctx.params.get("negative_prompt"))` unchanged — skipping `ctx.state["plan"]` entirely — whenever `_asset_axis(ctx)` is set (any non-`GENERAL` image or video asset kind), leaving `execute_asset_planning`'s own per-view guidance as the sole source of prompt enhancement for those jobs; `execute_planning` itself still runs unchanged (same progress event, same `AgentRun`/cost, same checkpoint) for a plain `GENERAL` job.
22. **A reference image's URL must actually be reachable by the provider making the request — `local`/`test`'s `s3_public_endpoint_url` (`http://localhost:9000`) never is, for an external HTTP API like aihubmix.** `localhost` always resolves to whatever machine is making the request; a real deployment's `s3_public_endpoint_url` is expected to be a real internet-reachable domain (a CDN/public bucket), where handing over a presigned URL is correct and cheap (the provider fetches once instead of every byte round-tripping through our own request body) — but in `local`/`test` a presigned URL there is silently unfetchable, so the provider gets nothing to condition on and falls back to generating from the prompt text alone. This exact failure mode produced a real "completely unrelated character" side/back completion job: `job_events` confirmed the per-view prompt fix (invariant above) had already landed correctly with no cross-view contamination, yet the actual output still ignored the attached front reference entirely, because the `image` field in the aihubmix request was a `localhost` URL aihubmix's servers could never reach. `Settings.embed_reference_images_as_base64` (`app_env in {"local", "test"}`) is the fix: `aihubmix_media._image_reference_urls` branches on it — the default (real deployments) keeps the presigned-URL behavior unchanged, `local`/`test` instead fetches the bytes (`s3.get_object`) and inlines them as a `data:<mime>;base64,<...>` URI, which aihubmix's own docs document as the intended alternative "for local files or private image scenarios." A reference over aihubmix's documented 20MB inline limit (`_MAX_BASE64_REFERENCE_BYTES`) falls back to the URL rather than guaranteeing failure either way. Scoped to the single image-to-image `image` field only — video's `frame_images`/`input_references` (`build_video_payload`) stay URL-only, since a video reference routinely exceeds any sane inline-body size.
23. **`/v1/images/generations` + an ad-hoc `image` field is not a documented AiHubMix contract for a Qwen model, and it does not reliably follow the reference** — even with invariant #22's base64 fix landed and confirmed reaching the provider, a live check (2026-08-19) still got "completely unrelated character" results: sending the exact same reference through that field only weakly steered the model (right gender, nothing else — wrong face, wrong clothes), and the *identical* prompt with no `image` field at all produced a similarly generic result, meaning the field's influence was near indistinguishable from noise. AiHubMix's own docs (`docs.aihubmix.com/en/api/Image-Gen`, "Qwen-Image-Edit") document a *different*, dedicated endpoint for this — `POST /v1/models/qianfan/qwen-image-edit/predictions` with body `{"input": {"prompt": ..., "image": <url-or-data-uri, 1-3 images>, "n": 1, "watermark": false}}` (response shape `{"output": [{"url": ...}]}`, always a URL in practice, never `b64_json`) — and a live check against that endpoint with the same reference and prompt preserved face/hair/uniform exactly while correctly rotating to the requested view. `AiHubMixMediaProvider._submit_image` now branches on `_is_qwen_model(self._model)` (a plain `"qwen" in model.lower()` check) whenever there's at least one reference: a Qwen model routes through `_submit_qwen_image_edit` (the real editing endpoint) instead of falling through to the OpenAI-shaped `/v1/images/generations` body. Two contract quirks specific to this endpoint, both found by a live 400 rather than in any doc: (a) no `size` field at all — every `_IMAGE_SIZE_BY_ASPECT` value tried was rejected with `image size is invalid`; this endpoint takes its output resolution from the input image instead, unlike the OpenAI-shaped call's mandatory `size`. (b) the output `url` must be downloaded with a **bare, header-less** `httpx.Client` — it's a pre-signed BCE (Baidu Cloud) object-storage link, not an AiHubMix one, and BCE's edge answers `400 MissingDateHeader` the moment *any* `Authorization` header rides along (as `self._client()` always attaches), since it then expects a paired `date`/`x-bce-date` header for BCE's own header-signature scheme instead of just trusting the URL's own query-string signature. **Two model families now leave `/v1/images/generations`, not one** — `_is_qwen_model` routes to the Qwen edit endpoint, and `is_gpt_image_2` routes a *referenced* request to `_submit_gpt_image_2_edit`, a multipart `POST /v1/images/edits` (its text-to-image path also overrides `size`/`quality`/`output_format` from `_GPT_IMAGE_2_SIZE_BY_ASPECT` / `_GPT_IMAGE_2_QUALITY_BY_TIER`). Every *other* model family still goes through the unverified-but-unchanged OpenAI-shaped path, since there is no live credential here to check whether it actually works for them either; don't assume it does just because Qwen's and gpt-image-2's versions of the same idea didn't.
24. **A retry can skip straight to `route_score` when there is genuinely nothing new to check.** `POST .../retry` (`api/v1/jobs.py::retry_job`) always resubmits `original.request_json` verbatim, so "input unchanged" is structural, not something the fast path has to verify itself — but that alone isn't enough to skip `safety`/`skill_context`/`planning`/`intent_router`/`asset_planning`. `fast_retry.build_seed(session, retry_job)` (`back/app/domain/jobs/fast_retry.py`) also requires the *previous* attempt to have been a genuine provider failure: `original.failure_code` in `{PROVIDER_TEMPORARY_FAILURE, PROVIDER_INVALID_RESPONSE, PROVIDER_TASK_FAILED}` (excludes `MISSING_REFERENCE`/`PROVIDER_TIMEOUT`/`QUALITY_REJECTED`/`MODERATION_REJECTED`) **and** at least one real `ProviderAttempt(status=FAILED)` row for it — a `no_candidate`/`retries_exhausted` dead end that never actually called a provider gets the same generic failure code but no such row, and still walks the full graph, since there's nothing to exclude and nothing gained by skipping planning. Scoped to `text_to_image`/`image_to_image`/the three video operations, and only when neither `asset_kind` nor `video_asset_kind` is set (`GENERAL`/unset) — a character/scene/cover job's `asset_planning`/`asset_output_advance` depend on per-pass state (`_current_character_view` and friends) this gate doesn't reconstruct. When eligible, `build_seed` returns the *already-resolved* `prompt`/`negative_prompt` (read back from the failed job's own `JobEventType.GENERATING` event payload — `execute_provider_generate` always writes this right before every provider call — rather than recomputed, since nothing re-ran `planning`) plus the set of providers that failed (`ProviderAttempt.provider` for that job), and `app.workers.pipeline._apply_fast_retry_seed` seeds `ctx.prompt`/`ctx.params["negative_prompt"]`/`ctx.state["tried_providers"]` before calling `WorkflowRunner.run(ctx, start_node_id=<the graph's one route_score node>)` — `execute_route_score`'s own same-job exclusion (`ctx.state.setdefault("tried_providers", set())`, invariant `zaolang-agent-gateway` #1) picks up the pre-seeded set unmodified, so the just-failed provider is hard-filtered out exactly the way a same-job provider retry already excludes one — no change to `router.py`/`intent_router.py`. A graph without exactly one `route_score`-typed node (a heavily customized template) silently falls back to the normal entry node — this is a fast path, never a correctness requirement.
25. **`Operation.VIDEO_ANALYSIS` is a `GenerationJob` with no output asset.** It is gated by the platform-config flag `video_analysis_enabled` (checked in `POST /generation-jobs`), takes its clip via the `video_analysis_source` upload purpose (video-only MIME, 150MB, ≤ 3 minutes — see `zaolang-media-assets`), runs `run_video_analysis` on the dedicated `video_analysis` queue, and walks `defaults.py::video_analysis_graph` — `safety → planning(allow_followup_question=False) → route_score → video_analysis_generate → settle_success`, with no `skill_context`/`intent_router`/`quality_check` (there is no tier/duration intent to route on and no image/video quality to judge on a structured text result). `execute_video_analysis_generate` mirrors `execute_provider_generate`'s routing/billing/cancel/retry skeleton but never registers an `Asset`: the provider's structured breakdown lands in `ctx.state["result_json"]`, which `settle_success` persists onto `GenerationJob.analysis_result_json` and `GenerationJobResponse.analysis` (typed `VideoAnalysisResult`, `None` until settled) echoes back; the full reserved credits are captured directly (`settlement_credits` only prorates `VIDEO_OPERATIONS`, which this deliberately isn't in). The provider call is synchronous today — a `pending` reply just lands in the failure/retry branch, so revisit that node before shipping an async video-understanding protocol. The consumer UI is `front/src/features/video-analysis/*` (its own studio/progress/result/history, listing via `GET /generation-jobs?operation=video_analysis`, no `draft_id`).
26. **An in-flight `AsyncProviderTask` has a hard wall-clock give-up.** `expire_stale_jobs` deliberately never touches a job with a live `AsyncProviderTask` row, so `poll_once()` itself enforces `async_tasks.MAX_POLL_DURATION_SECONDS` (2h from the task's creation): once exceeded without a terminal upstream answer, `_give_up_on_dead_upstream` logs `async_task_poll_budget_exceeded`, closes the `ProviderAttempt` as `FAILED`, and `_resume_failed`s the job with `failure_code="PROVIDER_TIMEOUT"` (releasing the reservation) — without it the heartbeat-every-15s poll and the reservation would both continue forever for an upstream that silently stopped answering. `PROVIDER_TIMEOUT` is excluded from `fast_retry.build_seed`'s eligible codes (invariant #24).
27. **Anything that wants to react to a job finishing hooks `completion.on_job_terminal`, not a call site.** `state_machine.transition` calls it on every terminal landing, inside the caller's transaction, so a reaction either commits with the terminal write or not at all. The pipeline, the async-polling worker and `pipeline._fail`'s crash path all funnel through `transition` — a hook wired into only some of them works until it silently doesn't. By the time it runs, credits are already captured or released, so **every reaction is individually isolated and may not fail the job**: it logs to `SystemLog` and swallows instead. Losing a downstream side effect is recoverable; turning a paid-for, finished job back into a failure is not. Today its only reaction is landing the result on a canvas (`zaolang-canvas`).
28. **`MediaGenerationKind` is a routing filter, not a label.** An `LlmProviderEndpoint` declares `create` or `edit`; an `edit` video model is hard-filtered out of a request that carries no video source (`router.py`'s `edit_model_requires_video_source`, see `zaolang-agent-gateway` invariant #1), and `GET /generation-jobs/models` hides `EDIT` capabilities from `text_to_video`/`image_to_video` so the forced-model picker can't offer one that would immediately be eliminated. That endpoint also now returns each model's `resolutions` / `default_resolution` studio tiers.
29. **A job's own record says which resolution it asked for and which it actually got.** `execute_route_score` and `execute_provider_generate` stamp `requested_resolution` / `adapted_resolution` / `adapted_vendor_resolution` / `resolution_adapt_kind` into the routing decision record and the `GENERATING` event payload, because the client sends a tier **ceiling** and each candidate model adapts it to its own vendor spelling (`providers.base.adapt_resolution_tier`: exact, else highest strictly lower, else last-resort lowest). Without those fields a downgraded render looks like a bug report with no evidence. Don't drop them to slim the payload — pricing reads the adapted value, not the requested one.

## Extension Points

- **Add a status**: add the value to `JobStatus` → add its in/out edges to `JOB_TRANSITIONS` (an empty frozenset for out-edges if it's terminal) → if terminal, add it to `TERMINAL_JOB_STATUSES` and handle settlement → update the frontend `types.ts` and trilingual status copy → the property tests automatically exercise the new state's transitions.
- **Add an event type**: add the value to `JobEventType` → call `append_event` at the right pipeline stage in `pipeline.py` (`public_message` is user-facing — never leak a provider name or an internal error) → add an icon and copy to the frontend timeline.
- **Add a queue**: register routing in `celery_app.py` → sync the Makefile's `dev-worker -Q` list and `infra/docker-compose.release.yml` / `infra/docker-compose.prod.yml` worker commands → sync the admin health page's queue list, or the backlog becomes invisible. A dedicated worker process (the poller) must keep `-n zaolang-poller@%h` so it does not share `celery@hostname` with `zaolang-worker`.
- **Integrate an async provider**: `GenerationProvider.submit()` returns `GenerationResult(pending=True, external_task_id=...)` once the remote task is created → implement `poll()` to do **one** status check (never a `while` loop holding a worker) → nothing else needs to change: `execute_provider_generate` recognizes `pending` and writes a checkpoint, and `poll_once()` handles heartbeat events, resumption, and timeout.
- **Change retry policy**: `tasks.py` only does bounded `retry` for transient infrastructure errors (DB/Redis/network); a `JobNotFoundError` (a broker entry pointing at an already-cleared job) returns `missing` immediately, no retry. Raising `max_retries` amplifies `effective_cost_micro_usd` (consumed by `intent_router`, see `zaolang-agent-gateway`) — sync the provider config's `retry_amplification` accordingly, and don't use this as a reason to bring back a weighted selection formula in code. After a DB wipe those leftover broker entries still occupy a worker slot until `make dev-purge-queues` (`app.scripts.purge_stale_celery`) drops them; do not `FLUSHDB` db0 (rate-limit keys share it). Celery results are not the progress source of truth — `task_ignore_result=True` — so a pile of `celery-task-meta-*` after Beat ticks or `missing` returns is leftover, not a second job log.
- **"Preview then upgrade"-style derived submissions**: don't add a candidate array or a new pending state to `GenerationJob` — `POST /generation-jobs/{id}/promote` (`back/app/api/v1/jobs.py`) shows this class of need can be modeled as an ordinary `jobs_service.submit()` call with different business preconditions (`retry` requires the original job to be failed/cancelled/expired at the same tier; `promote` requires the original to have succeeded at the `preview` tier and the target tier to no longer be `preview`). The lineage is tracked on dedicated nullable columns (`promoted_from_job_id`, kept separate from `retry_of_job_id` since the semantics differ: one is a same-tier resubmit after failure, the other is a tier upgrade after a successful preview) — no new `JobStatus`/`JobEventType` needed. "Waiting for the user to pick a preview" is frontend-local state between two independent job lifecycles, not part of the job state machine. Both paths inherit `submit()`'s `Draft.latest_job_id` update — a retry that leaves that pointer on the failed original is the bug that made a queued/succeeded notification reopen the first failure.
