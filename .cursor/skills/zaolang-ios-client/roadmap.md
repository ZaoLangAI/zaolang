# iOS Client Roadmap & Backend Contract Gaps

The planning-era document has been deleted; this file is the archive of milestone definitions, acceptance criteria, and backend-contract gaps. M0–M5 are all complete — this file survives as the record of "why we decided this at the time." Before starting any work past M6, read this first, especially the three decisions and the acceptance checklist below.

## Three Decisions That Had to Be Locked Before Starting (structural, not decidable mid-flight) — all three are locked and shipped

| Decision | Options | What shipped |
| --- | --- | --- |
| Session-renewal approach | A: client-side `zl_refresh` cookie takeover / B: backend adds a native refresh channel | **A** (`CookieCodec` + Keychain) |
| Credit purchasing | A: integrate StoreKit 2 / B: no purchase entry point, link out to the web app | **B** — `BillingView` shows balance/ledger read-only; when the balance is low or the user wants to buy, `UIApplication.shared.open` opens the web app's `/billing`; `POST /v1/credits/checkout` is never called |
| APNs push | Ship in v1 / defer, fall back to foreground polling | **Shipped in v1** — the backend added a `Device` model + `POST/DELETE /v1/me/devices`; the client's `PushManager` implements the full registration/tap-to-navigate chain; `back/app/domain/notifications/push.py`'s actual APNs send is still a logging placeholder (no real APNs certificate) |

## Milestones

- **M0 — Foundation** (done): the networking layer, `Page<T>` parsing, design tokens, the media-cache key strategy, trilingual copy integration.
- **M1 — Read-only closed loop** (done): discover (hero/masonry/infinite scroll/tags/sort/search), inspiration preview, work detail, lineage graph, profile, learn — all guest-accessible, no write operations.
- **M2 — Account & session** (done): `AuthSheet` login/register, `AppEnvironment.requireAuth`'s three-way "action recovery" semantics (run immediately if logged in / stash and resume if not / discard on cancel, never silently), like/bookmark/follow (optimistic updates), library (works/drafts/bookmarks/collections, four sections), the account area (`SettingsView`), the notification list, data export and deletion requests.
- **M3 — Creation closed loop** (done): the create hub (`CreateView`), the studio (`StudioView`/`StudioViewModel`, new and remix sharing one shape distinguished by `StudioMode`), asset upload (`UploadTransport` direct-to-presigned-URL), quoting (400ms debounce), submission (draft + generation job sharing one idempotency key), job detail (SSE + 5-second polling fallback, `JobDetailViewModel`), publish (`PublishView`, two confirmation checkboxes unchecked by default, default visibility `public_view_only`), and the persistent create-tab banner (`CreateJobBanner`).
- **M4 — Onboarding path** (done): three-screen onboarding (`OnboardingView`, the `iosOnboarding` i18n namespace, `UserDefaults` tracking whether it's been seen, independent of login state). Finer polish — a rewrite-suggestion chip, same-source recommendations during the wait, analytics — is undone but doesn't block usability; treat it as a future enhancement, not a gap.
- **M5 — Store readiness** (done): `PrivacyInfo.xcprivacy` (the privacy manifest), the `aps-environment` entitlement (currently `development` — switch to `production` before submission), `UIBackgroundModes: remote-notification`. App Store assets (screenshots, description copy), the age-rating questionnaire, and crash/performance monitoring (e.g. Crashlytics) still need manual setup in App Store Connect — they're outside the scope of code changes.
- **M6 and beyond (unscheduled, still undone)**: further push scenarios (silent push), StoreKit in-app purchases (should product reverse that decision), more collection-management actions, style presets, iPad and landscape, enhanced offline browsing, a share extension.

## Backend Contract Gaps (five total — two still open, one worked around, two resolved with new backend endpoints)

1. **Refresh tokens travel only via an httpOnly cookie** (still open, risk remains): `POST /v1/auth/refresh` only reads `Set-Cookie: zl_refresh` — there's no body/header fallback channel. Implemented per decision A (client-side takeover); the risk is that a backend change to cookie attributes silently breaks renewal — the cookie name and attributes are pinned as constants with a matching integration test, see invariant 4 in the `zaolang-ios-client` SKILL.md.
2. **APNs device registration endpoint** (resolved): the backend added the `Device` model in `back/app/models/platform.py` + `POST/DELETE /v1/me/devices` in `back/app/api/v1/devices.py`; `back/app/domain/notifications/push.py`'s `notify()` writes a notification row on job-terminal-state/remix/royalty-payout events, but `_dispatch_push` currently only logs (no real APNs certificate).
3. **Some lists have no cursor yet** (still open): only `GET /v1/works`, `GET /v1/credits/ledger` and `GET /v1/learn/posts` support `cursor`; `GET /v1/generation-jobs` (`limit` capped at 50), `GET /v1/notifications`, `GET /v1/drafts` (capped at 50), `GET /v1/me/bookmarks`, and `GET /v1/profiles/{handle}/works` only ever return one full page. The client's parsing layer uniformly wraps these in `Page<T>`; when `nextCursor` is `nil`, "load more" doesn't render — once the backend adds a cursor, the client needs zero changes.
4. **Payment compliance** (worked around): `POST /v1/credits/checkout` is a browser checkout flow, and the App Store requires IAP for in-app digital purchases. Product chose option B — `BillingView` never calls this endpoint; it shows balance/ledger/credit packages read-only, and the purchase entry point is `UIApplication.shared.open` linking to the web app's `/billing`, sidestepping the high-risk path of putting `checkout_url` inside an `SFSafariViewController`.
5. **SSE needed a client-side implementation** (resolved, simplified): `ZaolangKit/Streaming/` (`EventStreamClient`/`SSEReconnectPolicy`/`SSEFrameParser`) already had frame parsing plus 1s→2s→5s→10s→30s backoff reconnection since M0; `JobEventStream.swift` adds job-specific decoding via `jobEvents(jobID:)` on top of it. `JobDetailViewModel` **doesn't** implement a "fall back to polling after three consecutive reconnect failures" counter state machine — instead, SSE and an independent 5-second polling loop simply run in parallel indefinitely (SSE updates `status`/`progress` early when it arrives, polling guarantees alignment with server state within 5 seconds regardless, and a terminal state always triggers one final full `GET`). This simplification is correctness-equivalent and simpler to implement, but reproducing the exact "live connection unavailable, refreshing periodically" copy precisely would require redesigning this state machine.

## Global Acceptance Checklist (run through before merging any milestone)

- **Functional correctness**: a full code search for amount fields finds no `Double`/`Float`; IDs are never hand-written, always from backend responses; the `ref` vs. `source_work_id` paths are distinguishable in both code and UI; a private work always renders 404 as "doesn't exist or was withdrawn," never "no permission"; submitting a generation / retrying / checkout all carry a client-held `Idempotency-Key`; the cancel button only appears in a cancellable state, retry only in a terminal state; the publish page defaults to `public_view_only` with confirmation boxes unchecked.
- **Experience**: every new screen implements all six states (default/loading/empty/error/offline/logged-out); skeleton screens match real content height, no layout jump; an empty state always pairs "one explanatory sentence" with "one way out"; the studio's and publish page's commit buttons stay pinned above the bottom safe area, never scrolling away; the create tab shows a persistent banner whenever a non-terminal job exists.
- **Accessibility**: the same standard as web's `make test-a11y`/`make qa-visual` — 4.5:1 body-text contrast in light theme, 3:1 for large text; no truncation or horizontal overflow at the largest assistive text size; every VoiceOver icon button has an `a11y.*` label; no transition exceeds 50ms with reduced motion on; touch targets are at least 44×44pt.
- **Performance**: cold start to the discover page's first frame is under 1.5s (including session restoration); the masonry feed scrolls at 60fps with no dropped frames; memory doesn't grow unbounded during extended scrolling on discover; entering the detail page to video playback start is under 1s.
- **Consistency with web**: copy keys stay aligned with `front/src/i18n/messages/`, with any new key added in all three languages at once; enum values follow `back/app/models/enums.py`; dark-theme colour values are compared side-by-side against web screenshots; the contract follows `back/openapi.json` — after the backend runs `make openapi`, the client syncs and cross-checks.

## The D3/D4 Studio Shape (implemented, `StudioView`/`StudioViewModel`)

The studio is one screen with two shapes, distinguished by `StudioMode` — never split into two Views:

| | New (`StudioMode.new(operation:initialPrompt:)`) | Remix (`StudioMode.remix(sourceWorkID:)`) |
| --- | --- | --- |
| Input | an operation type + an optional prefilled prompt (used by the inspiration preview's "create with this prompt") | only `sourceWorkID` — `StudioViewModel.load()` fetches `WorkDetail` itself |
| Assets | only the user's own uploaded reference images (`needsReferenceImage`, needed only for image-to-video) | the same upload logic, plus the source work's `reusableParams.prompt`/`negativePrompt` prefilled into the form |
| Attribution prompt | none | an "I'll keep the original author's attribution" confirmation checkbox (`rightsSection`, must be checked to submit) |
| Submission body | `sourceWorkID` is `nil` | the draft carries `sourceWorkID`, used at publish time to inherit the license and write the lineage edge |

Single-column layout: a source card (when remixing) → operation-type segmented control → prompt → reference images (as needed) → aspect ratio/duration → quality tier → attribution confirmation (when remixing), with the quote and submit button pinned above the bottom safe area via `.safeAreaInset(edge: .bottom)`.

## The In-Progress-Job Banner (implemented, `CreateJobBanner`)

`CreateView` mounts a persistent `CreateJobBanner` at the top: `AppEnvironment.activeJobs` (non-terminal jobs, sorted by creation time, taking the first) drives a progress bar, tapping it pushes to `CreateRoute.jobDetail`; once a job reaches a terminal state, the banner keeps showing as a result notice for 8 seconds, dismissible by the user via the top-right close button or automatically after 8 seconds (`TimelineView(.periodic(from:by:))` re-evaluates periodically — no extra timer state needed). Job-tracking state lives in `AppEnvironment.trackJob(id:)`/`trackedJobs`, called once after a successful submit/retry, polling every 5 seconds until terminal — independent of the job-detail page's own SSE subscription; the banner keeps animating even after leaving the job-detail page.
