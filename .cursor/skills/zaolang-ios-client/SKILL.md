# ZaoLang iOS Client

## Scope

`ios/` is a native client, independent of `front/` (Next.js), sharing the same backend contract (`back/openapi.json`). M0 (foundation) through M5 (store-readiness) are complete — see [roadmap.md](roadmap.md) for milestone history, acceptance criteria, and backend-contract gaps (scope beyond M6 is unscheduled and not yet built). By product decision, credit purchases **don't integrate StoreKit** — the app shows balance/ledger read-only and links out to the web app to buy.

**No `admin*` back-office capability is implemented here** — admin uses a separate login and a separate cookie that a consumer token can't enter. This is a deliberate boundary with `zaolang-admin-console` / `zaolang-admin-ops`, not an oversight.

## Invariants

1. **Generated artifacts are never hand-edited**: `Assets.xcassets/Colors/*.colorset` and `Localizable.xcstrings` are both script output, sourced from `front/src/app/globals.css` and `front/src/i18n/messages/*.json`. To change a colour or a string, change the source and rerun the matching script.
2. **Never invent a new i18n key.** `gen-strings.py`'s `NAMESPACES` list is the current set of exported namespaces (`discover`/`work`/`workPage`/`lineagePanel`/`learnPage`/`profilePage`/`states`/`actions`/`a11y`/`nav`/`visibility`/`license`/`theme`/`region`/`brand`/`auth`/`collectionPage`/`createPage`/`remixPage`/`job`/`jobPage`/`publishPage`/`settingsPage`/`billingPage`/`notificationsPage`/`notificationBody`/`credits`/`iosOnboarding` — `iosOnboarding` is iOS-only, with no web equivalent). Any copy iOS needs must already exist in `front`'s trilingual message files (the three languages' key sets match — see `zaolang-i18n-region`); iOS must never unilaterally invent a term or leave a Chinese-only placeholder. If a needed namespace isn't in the list, add it there first and rerun the script.
3. **`ApiError` merges 404 and `WORK_PRIVATE` into a single case**: any screen rendering "doesn't exist" copy goes through this one path — never leak a private work's existence with "no permission" wording, matching the web client's rule exactly.
4. **`zl_refresh` session renewal is handled by client-side cookie takeover**: `URLSession`'s default cookie container is disabled (`httpShouldSetCookies = false`); `CookieCodec` manually parses `Set-Cookie`, stores it in Keychain, and manually attaches the `Cookie` header on outgoing requests. Concurrent 401s are single-flighted into one refresh by `SessionManager`. If the backend ever changes `zl_refresh`'s domain/path/attributes, this silently breaks renewal — any such change must be communicated to iOS.
5. **Reduced motion reads `@Environment(\.zlMotion)`, never `accessibilityReduceMotion` directly**: `zlMotion` is the merged result of "system reduce-motion OR the server-side `reduce_motion` preference," written centrally by `RootView`. Any new `.animation`/`withAnimation`/custom `.transition` must gate on this environment value, skipping or using a near-zero duration when it's true.
6. **A Swift-synthesized-init visibility trap**: if a View struct mixes in a `private let`/`private var` **without a property wrapper** (e.g. a fixed layout constant), the compiler-synthesized memberwise initializer is downgraded to `private` too, so other files can't call that View's initializer. `@State`/`@GestureState` and other wrapped properties marked `private` are unaffected (the synthesized init is generated from the wrapped-value type, not the wrapper itself). Any View constructed from another file that mixes in a non-wrapped private stored property must hand-write its `init`.
7. **`ref` and `source_work_id` are two different concepts**: an inspiration reference doesn't create a lineage edge or inherit a license; a remix creates a lineage edge and triggers royalty payback. The inspiration preview's "create with this prompt" (`InspirationPreviewSheet.onCreateFromPrompt`) routes to `StudioMode.new(operation:initialPrompt:)` — prefilling only the prompt, no `source`; a work detail page's "remix" routes to `StudioMode.remix(sourceWorkID:)` — `StudioViewModel` uses this to decide whether to show the "keep original author's attribution" toggle and asset inheritance. Both paths share the same `StudioView`/`StudioViewModel` — don't split them into two Views.
8. **Pagination always parses through `Page<T>`**: only `GET /v1/works`, `/v1/credits/ledger`, and `GET /v1/learn/posts` actually support `cursor` on the backend; every other `Page`-shaped list endpoint only has `limit` ("fetch everything in one page"). Even for a "fetch everything" endpoint, the parsing layer still wraps it in `Page<T>` — once the backend adds a cursor, the client needs zero changes. Don't write a separate non-paginated parser for a currently-single-page endpoint. The exception is endpoints whose backend response is a bare JSON array rather than a `Page` envelope: `/v1/characters` and `/v1/scenes` decode as `[CharacterResponse]`/`[SceneResponse]` in `APIClient+AssetLibrary.swift` — wrapping those in `Page<T>` would fail to decode.
9. **The lineage graph defaults to depth 3** (`LineageViewModel.depth`), unlike the backend's default of 4 — a phone screen can't fit 4 levels. This is a deliberate client-side decision; confirm the wireframe intent hasn't changed before touching it.
10. **Amounts are integers, and enum values follow `back/app/models/enums.py`** — the same rule as the rest of the repo. `RawOrUnknown<T>` is the graceful-degradation path for when the backend adds a new enum value, not noise to ignore.
11. **The locally installed XcodeGen 2.46.0 has a real bug where the top-level `resources:` key does nothing** (reproduced with a minimal project — this is a genuine defect in that version, not a config mistake): it never emits a `PBXResourcesBuildPhase`, so `Assets.xcassets`/`Localizable.xcstrings` never get compiled into the app, and colours/copy all fail to load. `project.yml` already works around this — resources go into the target's `sources:` with an explicit `buildPhase: resources`. Any new resource file must follow the same pattern — don't switch back to the top-level `resources:` key.
12. **A custom `Info.plist` must hand-write `CFBundleIdentifier`/`CFBundleExecutable`/`CFBundlePackageType`/`CFBundleName`/`CFBundleInfoDictionaryVersion`**: with `GENERATE_INFOPLIST_FILE: NO` in `project.yml`, Xcode won't auto-inject these five keys, and missing any of them blocks install on simulator/device (`Invalid parameter ... installURL`). Already added in `App/Resources/Info.plist` — don't remove them.
13. **`Operation` collides with `Foundation.Operation`(`NSOperation`)**: any file that both `import Foundation` (even indirectly, for `Data`/`URL`/`UUID`) and `import ZaolangKit`, then writes a bare `Operation`, gets an "ambiguous for type lookup" error. **`ZaolangKit.Operation` doesn't disambiguate it** — `ZaolangKit` also has an internal namespacing enum `public enum ZaolangKit`, so that spelling resolves as "a nested type not found in that enum," a different error. The only clean fix: define the alias using a bare `Operation` in a file that doesn't `import Foundation` (already done: `Support/GenerationOperation.swift`'s `typealias GenerationOperation = Operation`), and have any file that needs `Foundation` reference `GenerationOperation` instead. `Routes.swift` has no `Foundation` dependency, so it deliberately keeps the bare `Operation`. `Operation` now has six cases including `imageToImage`/`audioGeneration` (previously unrepresented on iOS — the create hub only exposed `textToVideo`/`imageToVideo`), plus `isImage`/`isVideo` computed properties; `ImageAssetKind` (`general`/`character`/`scene`/`cover`) is a sibling enum for the asset-kind dimension layered on top of `text_to_image`/`image_to_image` — mirror any backend addition to both in the same change. **`character` is one case, not three**: a character's front/side/back turnaround views are a separate `CharacterViewAngle` enum (`general`/`front`/`side`/`back`), named via `GenerationParams.characterViews` — `StudioViewModel` only ever submits the default (`nil`, meaning front); generating the remaining views goes through `StudioViewModel.completeViews(for:)` instead (see invariant below), never a studio-form picker.
14. **The login wall for recovering an interrupted action uses `AppEnvironment.requireAuth`; never resurrect the old `LoginWallSheet` pattern (removed)**: any write-action entry point calls `environment.requireAuth(actionLabel:) { /* the actual action */ }` — if already logged in, the closure runs immediately; if not, `AuthSheet` appears, and on successful login/register the closure runs automatically exactly once; if the user cancels, the closure is discarded and never runs silently. Wrap any new "unavailable while logged out" button this way — don't invent a second login-wall UI.
15. **`ios/README.md` is staler than this skill**: it still describes the M0/M1 read-only scope, names `LoginWallSheet` (removed, see invariant 14), and says `Media/` and SSE are unwired. When the two disagree, this skill and the code win; don't copy README wording into new skill text without re-checking `ios/App/Sources/`.
16. **Every displayed timestamp goes through `ZLClock`, never `Date.formatted` directly.** `ios/App/Sources/Common/Date+ZL.swift` pins `dateTime` / `time` / `date` to `Asia/Shanghai`, mirroring web's `DISPLAY_TIME_ZONE` (`front/src/i18n/routing.ts`, see `zaolang-i18n-region` invariant #6): stored timestamps stay UTC and the platform has one wall clock, so a job that finished at 14:03 reads 14:03 on every device and in every language. Language changes the copy, not the clock. Seven screens already route through it (billing, notifications, job detail, work detail, reusable params, draft spec, debug session) — a new screen that formats a `Date` with the system default would silently disagree with all of them for a user outside UTC+8.

## Auth & Write Operations

- **`AppEnvironment.requireAuth(actionLabel:action:)`** is the sole login-wall primitive (see invariant 14). `actionLabel` drives the "here's what you're about to do" copy at the top of `AuthSheet` and must be an existing i18n key (e.g. `L10n.t("work.like")`) — never a hardcoded English/Chinese literal.
- **`StudioMode` is the sole entry point for the studio**: `.new(operation:initialPrompt:)` (three of the five cards on the create hub `CreateView.modeCards` — **图片创作** (`.textToImage`; `StudioViewModel.effectiveOperation` derives `.imageToImage` the moment a reference is attached, mirroring web's `GenerationStudio`) / text-to-video / image-to-video — plus the inspiration preview's "create with this prompt") and `.remix(sourceWorkID:)` (a work detail's "remix") both share `CreateRoute.studio`, and both must switch to the Create tab before pushing (see `RootTabView.startRemix` / `DiscoverView`) — never push the studio directly onto another tab's stack. The hub's other two cards do not open the studio: "remix" just `selectTab(.discover)` behind `requireAuth`, and "learn-publish" switches to the Learn tab and pushes `LearnRoute.publish`. There is no hub card for publishing a work — `CreateRoute.publish(draftID:)` is only reachable from a draft. `StudioViewModel`'s YAGNI comment about `text_to_image`/`video_to_video` having no UI entry point was updated once 图片创作 shipped — `video_to_video` now has no `.new` entry but is submitted by remix. **Remix operation follows the source medium**: `StudioViewModel.remixOperation(for:)` maps a video source to `.videoToVideo`, an image source to `.imageToVideo`, an audio source to `.audioGeneration` (falling back to `.textToVideo` when the media type is unknown), matching web's per-media-type `RemixStudio` pick and the backend's `attach_licensed_source_video` — do not write "remix is always `image_to_video`" back into skills.
- **`StudioViewModel.completeViews(for:)` is the iOS "补全侧面/背面" entry point**, wired from the character `LibraryPickerSheet` row action (see Key Paths above) rather than a standalone character-library screen (iOS has none yet). It submits an `image_to_image` job with `characterViews: [.side, .back]` and the character's `frontReference.assetID` as the sole reference, polls `fetchGenerationJob` until `status.value?.isTerminal`, then re-fetches the character via `fetchCharacter(id:)` and replaces it in `characters`. **iOS is now the only client that offers this** — web dropped view completion (its `character-library.tsx` has a single reference slot and no `completeViews`; `lib/characters.ts`'s `canCompleteViews` survives only for tests and this caller), so don't justify a change here by "matching web", and don't delete the API path on the assumption web still uses it. This is a separate one-off submission, not a `StudioViewModel.submit()` call — it doesn't create a `Draft`/`Work` and reuses its own idempotency key (`"complete-views-\(character.id)"`), not the draft-scoped one `submit()` uses.
- **Push**: `PushManager.shared.requestAuthorizationAndRegister()` is only called when the user explicitly taps "enable notifications" in `SettingsView`'s notification section — it is the single call site; `OnboardingView` does not request push, and cold start never triggers the system permission prompt automatically. Once a device token is obtained, `AppEnvironment.registerPushToken` calls `POST /v1/me/devices`; on sign-out, `AppEnvironment.signOut()` first `DELETE`s that device record.
- **Credit purchases**: by product decision, StoreKit isn't integrated — `BillingView` only shows balance/ledger/credit packages read-only, and its "buy" button opens the web app's `/billing` via `UIApplication.shared.open`. Never add a `POST /v1/credits/checkout` call or an embedded `SFSafariViewController` checkout on this path. Paid-remix unlocks similarly link out to the web `/work/{id}`; the skill marketplace isn't integrated in this version.

## Out of Scope (M6+, unscheduled)

Push scenarios beyond APNs (e.g. silent push for badge refresh), StoreKit in-app purchases (should product reverse that decision), iPad and landscape, enhanced offline browsing, a share extension, and the style-preset library. Before starting work here, read [roadmap.md](roadmap.md) to confirm no new product decision has overridden the current defaults (session renewal, credit purchasing, and APNs have all been implemented per the documented defaults).

## Extension Points

- **Align discover sort with web's three options** (`recent`/`popular`/`remixed`): iOS's wall defaults to `recent`, web defaults to `popular`; both Heroes are pinned to `popular`. There is no separate `DiscoverSort` — `DiscoverViewModel.sort` is the `WorksSort` enum from `Models/Work.swift`, passed through `APIClient.listWorks(_ query: WorksQuery)` (`APIClient+Works.swift`), and `DiscoverView` iterates `WorksSort.allCases` for the picker. Adding a fourth option means updating `WorksSort` (and `sortLabel` in `DiscoverView`) plus the trilingual `discover.sort*` keys together.
- **Add a new read endpoint**: add a method to `ZaolangKit/Networking/APIClient+*.swift` → add a new DTO to `Models/` if needed → `cd ios/Packages/ZaolangKit && swift build` to self-verify → call it from the view layer.
- **Add a new write operation/screen**: create a new `App/Sources/<Feature>/` directory following `Create/`'s split (`*View` + `*ViewModel`); wrap any write-action entry point in `environment.requireAuth` (see "Auth & Write Operations" above); add the matching Route case to `Shell/Routes.swift`; wire it up in `RootTabView`'s `discoverDestination`/`createDestination`/`libraryDestination`/`learnDestination`-style `@ViewBuilder` functions.
- **Add a string**: first confirm the key already exists across all three of `front/src/i18n/messages/{zh-CN,en,ja}.json`; if the namespace iOS needs isn't exported yet, add it to `ios/tools/gen-strings.py`'s namespace list and rerun the script; consume it in code via `L10n.t("namespace.key")`.
- **Add a colour token**: first confirm both `:root` and `[data-theme='dark']` in `front/src/app/globals.css` define the variable, rerun `gen-colors.py`, and consume it via `Color.zl.*` (`Color+ZL.swift`) — never add a raw colour literal.
- **Change navigation structure**: each of the four tabs owns an independent `NavigationPath` (`AppRouter`); cross-tab navigation logic lives in `AppRouter.handle`/`selectTab`; Universal Links parsing lives in `Shell/DeepLink.swift`, which ignores any `/{locale}/` prefix in the URL — the destination uses whatever language the app is currently in.
- **Fill in the six states for a new screen**: `Common/LoadableState.swift` covers `loading/loaded/empty/failed`; `offline` and "logged out" are orthogonal dimensions — `offline` reads `environment.reachability.isOffline` (the global banner is already wired up in `RootTabView`, so a single screen usually doesn't need to redraw it), and "logged out" is handled by wrapping the write action in `environment.requireAuth` — don't add a "logged out" case at the data layer. An empty state must always pair "one explanatory sentence" with "one way out" — never just "no data."
