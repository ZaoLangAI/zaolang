# Agent Gateway — Extended Reference

Not auto-loaded with the skill. Read this for the LLM failover pool, MiniMax H3 contract details, role/binding mechanics, and `node_id` write-back — the parts of `zaolang-agent-gateway` that come up less often than the routing core in `SKILL.md`.

## Invariants (continued — #10–17)

10. **The LLM inference endpoint uses its own independent failover pool** (`llm/failover.py`), running in parallel with `router.py`'s selection routing for image/video/audio generation — don't mix the two candidate-selection systems. They share the `llm_providers` store but are strictly partitioned by `kind`. When an `AgentProfile` (judgment or assist role) has a default/backup endpoint bound, failover only happens between those two manually chosen providers; without a binding, it falls back to the shared pool of providers supporting the target model.
11. **A role can only come from `ROLE_PRESETS`.** Creating an agent in admin picks a role from a dropdown, not free text: a workflow node's type is a code whitelist, so an agent built with a role no node type recognizes will never execute. To make a new judgment-role role runnable, either give it a dedicated node type or use the generic `custom_agent` node (whose role comes from `config.agent_role` at runtime).
12. **A workflow binds by agent id, and the bound agent must match the role the node requires.** A single role can have multiple agents (admin groups them by role, but the group is just a heading — the only actionable object is the agent). A node config's `agent_id` / `selector_agent_id` stores `AgentProfile.id`, never a name or key — names can change anytime, but a published graph must keep pointing at the same agent. A role mismatch errors at publish time (`workflow_templates.service._binding_errors`) and is also rejected at runtime, falling back to the role's default agent (`resolve_prompt`) — running safety review through a copy agent would treat whatever it produces as a pass/fail verdict. An empty binding means "this role's default agent."
13. **Media endpoints have no LLM primary/backup/concurrency semantics**: they declare only one model, interface protocol, input/output modalities, timeout, and enabled state. Primary/backup ordering and concurrency scheduling only exist for general-purpose endpoints.
14. **Native video providers follow a per-model `NativeVideoModelProfile`** (`aihubmix_media.py`): MiniMax H3 is 4–15 seconds, ten aspect ratios (`16:9`/`9:16`/`1:1`/`4:3`/`3:4`/`21:9`/`3:2`/`2:3`/`9:21`/`adaptive`), resolution `2K` or `768P` (create/new still sends one of those — never hardcoded in the provider); `wan2.7-videoedit` is 2–10 seconds, five aspect ratios (no `21:9`/`3:2`/`2:3`/`9:21`/`adaptive`), `720p`/`1080p` (no explicit `resolution` sent, provider default applies); `doubao-seedance-2-5-260628` is 4–30 seconds or `-1` (`supports_auto_duration=True` — the model picks a length itself), six aspect ratios + `adaptive`, `480p`/`720p`, and additionally takes a `generate_audio` toggle (`supports_generate_audio=True`) for a native soundtrack baked into the clip. The create response reads `id`, and status/output reads `output[].result_id` — **except** `doubao-seedance-2-5-260628`, whose own AiHubMix schema documents `poll_path: /ai/v1/videos/{id}` with the output URL inlined in the poll response instead of a separate `/content` call (`NativeVideoModelProfile.poll_style="videos_inline"`, unverified against a live credential — see `_poll_native_videos_inline`). Image/video references generate short-lived signed URLs from platform-private assets; `input_references` and `frame_images` are mutually exclusive — `frame_images` is an H3-only concept, `wan2.7-videoedit`'s MiniMax schema has no such field. **`wan2.7-videoedit` with a reference does not use MiniMax `input_references` at all.** That facade only accepts `image_url` / `video_url` / `audio_url` (live create 400 on `video`, `job_01m163ththh5yer79dtmv0q85d`); the gateway then forwards the facade type unchanged into Wan's `input.media[].type`, which only accepts `video` / `reference_image` (live poll failure on `video_url`, `job_01m1608wr7hm49wzdggkynz6ay`). The published `/ai/v1/videos` `extra` field is ignored for this mapping. The shape that create+completed on a live credential (2026-08-29) is `POST /v1/videos` with `extra_body.input.media` (Wan's enum) — poll that task on `/v1/videos/{id}`, never `/ai/v1/tasks/{id}` (404). Do not merge product `GenerationRequest.extra` into `extra_body`. H3 stays on `/ai/v1/videos` with `video_url` / `image_url`. Incompatible physical parameters get eliminated at the hard-filter routing stage — never left for the provider to error on. **Resolution is hard-filtered only when the request explicitly carries `video_options.resolution`**; an omitted value must not be treated as `2K`, or cheaper edit models drop out of the remix candidate set. The hard filter still keys on the **model name** via the profile table (`minimax-h3` / `wan2.7-videoedit` / `doubao-seedance-2-5-260628`) — don't change it to key on `protocol` alone. `dmxapi_media.py` keeps its own, entirely separate profile table (`VideoModelProfile`/`ImageModelProfile`) for its four models — the two providers never share a lookup, and `media_endpoints.py::dynamic_capabilities` picks which one to query purely off `endpoint.protocol`.
15. **Media `protocol` is an HTTP-contract standard name, not a gateway provider name.** The dropdown shows OpenAI / MiniMax / ComfyUI / DMXAPI, etc.; AiHubMix's image/audio API is OpenAI-compatible, so it shows as **OpenAI**. Implemented so far: `openai` (text-to-image, image-to-image, audio, and video via the OpenAI Videos API `/v1/videos`), `minimax` (native video contract via a per-model profile table — text-to-video/image-to-video/video-to-video, e.g. MiniMax H3), `dmxapi` (DMXAPI's own `/v1/responses` task envelope — the one deliberate exception to "never name a protocol after a vendor," since this specific envelope shape is DMXAPI's own invented convention rather than a shared standard; see invariant #18). `wan2.7-videoedit` is configured as `minimax` for catalog/profile limits, but a request that actually carries a reference is internally routed onto the OpenAI Videos path with `extra_body.input.media` (see invariant #14) — `protocol=openai` on that endpoint is not required. `comfyui` / `google` / `ark` / `kling` are catalogue placeholders only — an unimplemented protocol must never enter the `dynamic_capabilities` catalogue, and silently falling back to OpenAI is forbidden. `openai` and `minimax` instantiate `AiHubMixMediaProvider`, branching internally by `protocol` (and, for Wan edit, by model+reference); `dmxapi` instead instantiates the wholly separate `DmxApiMediaProvider` (`media_endpoints.py::_factory` dispatches on `protocol`) — the two providers share no HTTP-shape code because DMXAPI's contract (see invariant #18) is not a variant of AiHubMix's.
16. **`AgentRun.node_id` is written back by the workflow engine — an agent function never sets it itself.** Before calling an executor, `WorkflowRunner._execute_node` records the prior value of `ctx.state["_last_agent_run_id"]`; after the executor runs, if that value changed (meaning this node produced a new `AgentRun`) and it isn't a `dry_run`, it runs a single `UPDATE ... SET node_id = :node_id` on that row — no agent function needs, or should, take a `node_id` parameter. The product sandbox is a real job (`dry_run=False`), so this write-back happens there too, as normal. `RoutingDecision.agent_run_id` follows the same pattern: `select_provider()`'s `AgentOutcome.agent_run_id` passes through into `RoutingDecision`, and `nodes.py::execute_route_score` sets it into `ctx.state["_last_agent_run_id"]` so this LLM call's routing score also attaches to the `route_score` node — without changing `intent_router.select_provider()`'s own call contract.
17. **The product sandbox uses real media providers, same as the consumer app.** Editor trial runs no longer have a `live_provider` toggle; `WorkflowContext.dry_run` is reserved for unit-test graph walks only. Never push a full prompt to the consumer-facing public SSE stream — admin review reads from `AgentRun.input_json` / `JobEvent.payload` instead.
18. **DMXAPI (`dmxapi_media.py`) is a second real media provider, independent of AiHubMix, speaking one unified `POST /v1/responses` envelope for everything** — a synchronous image family (`doubao-seedream-5-0-pro-260628`: text-to-image/image-to-image, the latter covering both a single-reference edit and 2–10 image "multi-image fusion") and an async submit-task-then-poll video family (`MiniMax-H3`, `doubao-seedance-2-5-260628`, `wan3.0-video`, and `MiniMax-H3`'s video-regeneration mode). The request/response *body* shape differs per model family, so `DmxApiMediaProvider` dispatches internally by `model` (`extract_task_id`/`_poll_result`/`_build_video_body` each branch on it), the same way `AiHubMixMediaProvider` dispatches by `capability_tag`/`protocol`. Polling reuses the same endpoint with the `model` swapped for that family's own `"{family}-get"` id (`MiniMax-H3-get` / `seedance-2-5-get` / `wan3.0-get`) and `input` holding the task id. **`MiniMax-H3-video_regeneration` only upscales a source clip that already meets MiniMax-H3's own 768P output spec (audio track, 24fps, dimensions divisible by 32, area ≤768×1344, 107–362 frames) to 2K — it is not a general user-video-editing capability**, and it cannot faithfully replay a past job's full original multi-modal input (the platform does not persist that), so `_build_minimax_h3_regeneration_body` only reconstructs the prompt plus the one `frame_type="base_video"` reference; anything beyond a plain-prompt original generation will fail upstream. That model also has no connectivity-safe probe body (`dmxapi_media.probe_video_body` raises for it) — `connectivity.py` must return `error_code="no_capability"` rather than guessing a request. Every response-parsing function in this module is written to tolerate a few plausible shapes rather than betting on exactly one, and says so in its docstring — **none of it has been exercised against a live DMXAPI credential yet**; fix the specific function (not the whole module) once a real call disagrees, same "verify before trusting the docs" posture as `_submit_qwen_image_edit`/`_uses_wan_openai_edit` in `aihubmix_media.py`. `VIDEO_RESOLUTIONS` (`platform_config/schemas.py`) had to widen to carry three vendors' differently-cased resolution strings side by side (`480p`/`720p`/`1080p` for DMXAPI's doubao models, `480P`/`720P`/`1080P` for `wan3.0-video`, `768P`/`2K` for MiniMax) — never normalise the casing, the upstream gateway matches on the literal string. `back/app/providers/model_catalog.py`'s `VENDOR_MODEL_CATALOG` (surfaced read-only via `GET /admin/llm-providers/catalog`) is a **pure admin-picker convenience** layered on top of this — a curated "service provider → known model" list that pre-fills `LlmProviderEndpointUpsertRequest` fields in `/admin/models`' `VendorModelPicker`, never itself validated against or enforced at save time; the free-text "custom" path (today's only behaviour before this catalogue existed) is unaffected and always available.

## Prompt & Model Binding

Each agent's `SYSTEM_PROMPT` has migrated to a versioned `AgentSkill`. Model binding is managed only through `/admin/models`'s `llm_providers` catalogue plus `/admin/agents`'s `AgentProfile`: judgment-role (`judgment`) and assist-role (`assist`) agents share the same form — manually choose a default provider, an optional backup provider, and a model both support; a non-default agent with empty sampling fields inherits its role's default `AgentProfile`. `assist` is just a semantic label for the `copy` role (generating/polishing copy, not a pass/fail judgment) and doesn't change how binding works. **There is no default model name in code**; an unbound agent's `complete()` raises `ProviderTemporaryFailure` immediately — it never guesses `models[0]` or hardcodes kimi/doubao/ling, and never returns a fabricated result.

The gateway **has no embedding model** — semantic search uses a local deterministic implementation (see `zaolang-discovery-search`).
