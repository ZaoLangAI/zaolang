# Agent Gateway — Extended Reference

Not auto-loaded with the skill. Read this for the LLM failover pool, MiniMax H3 contract details, role/binding mechanics, and `node_id` write-back — the parts of `zaolang-agent-gateway` that come up less often than the routing core in `SKILL.md`.

## Invariants (continued — #10–20)

(This file's numbering is its own series — SKILL.md's own #10 is the streaming rule; cross-skill references to "agent-gateway reference #N" mean this list.)

10. **The LLM inference endpoint uses its own independent failover pool** (`llm/failover.py`), running in parallel with `router.py`'s selection routing for image/video/audio generation — don't mix the two candidate-selection systems. They share the `llm_providers` store but are strictly partitioned by `kind`. When an `AgentProfile` (judgment or assist role) has a default/backup endpoint bound, failover only happens between those two manually chosen providers; without a binding, it falls back to the shared pool of providers supporting the target model.
11. **A role can only come from `ROLE_PRESETS`.** Creating an agent in admin picks a role from a dropdown, not free text: a workflow node's type is a code whitelist, so an agent built with a role no node type recognizes will never execute. To make a new judgment-role role runnable, either give it a dedicated node type or use the generic `custom_agent` node (whose role comes from `config.agent_role` at runtime).
12. **A workflow binds by agent id, and the bound agent must match the role the node requires.** A single role can have multiple agents (admin groups them by role, but the group is just a heading — the only actionable object is the agent). A node config's `agent_id` / `selector_agent_id` stores `AgentProfile.id`, never a name or key — names can change anytime, but a published graph must keep pointing at the same agent. A role mismatch errors at publish time (`workflow_templates.service._binding_errors`) and is also rejected at runtime, falling back to the role's default agent (`resolve_prompt`) — running safety review through a copy agent would treat whatever it produces as a pass/fail verdict. An empty binding means "this role's default agent."
13. **Media endpoints have no LLM primary/backup/concurrency semantics**: they declare only one model, interface protocol, input/output modalities, `generation_kind` (`create` / `edit` — forced back to `CREATE` for `kind="general"`, and a hard-routing filter, see SKILL.md invariant #1), timeout, and enabled state. Primary/backup ordering and concurrency scheduling only exist for general-purpose endpoints. Timeout bounds moved with the slow image models: `LLM_ENDPOINT_TIMEOUT_MS_DEFAULT` is 90 000 ms and `LLM_ENDPOINT_TIMEOUT_MS_MAX` 600 000 ms (was 30 s / 120 s), and an image-output media endpoint additionally has a floor, `MEDIA_IMAGE_TIMEOUT_MS_MIN` 90 000 ms, enforced on upsert and healed for endpoints already stored below it.
14. **Native video providers follow a per-model `NativeVideoModelProfile`** (`aihubmix_media.py`): MiniMax H3 is 4–15 seconds, ten aspect ratios (`16:9`/`9:16`/`1:1`/`4:3`/`3:4`/`21:9`/`3:2`/`2:3`/`9:21`/`adaptive`), resolution `2K` or `768P` (create/new still sends one of those — never hardcoded in the provider); `wan2.7-videoedit` is 2–10 seconds, five aspect ratios (no `21:9`/`3:2`/`2:3`/`9:21`/`adaptive`), `720p`/`1080p` (no explicit `resolution` sent, provider default applies); `doubao-seedance-2-5-260628` is 4–30 seconds or `-1` (`supports_auto_duration=True` — the model picks a length itself; note this `-1` path exists on the profiles/builders of both providers but is not reachable from the product path: `GenerationParams.duration_seconds` is `ge=0` in `api/schemas/jobs.py` and `nodes.execute_provider_generate` clamps any video duration `<4` up to 4), six aspect ratios + `adaptive`, `480p`/`720p` (AiHubMix only — the DMXAPI profile of the same model also allows `1080p`), and additionally takes a `generate_audio` toggle (`supports_generate_audio=True`) for a native soundtrack baked into the clip. The create response reads `id`, and status/output reads `output[].result_id` — **except** `doubao-seedance-2-5-260628`, whose own AiHubMix schema documents `poll_path: /ai/v1/videos/{id}` with the output URL inlined in the poll response instead of a separate `/content` call (`NativeVideoModelProfile.poll_style="videos_inline"`, unverified against a live credential — see `_poll_native_videos_inline`). Image/video references generate short-lived signed URLs from platform-private assets; `input_references` and `frame_images` are mutually exclusive — `frame_images` is an H3-only concept, `wan2.7-videoedit`'s MiniMax schema has no such field. **`wan2.7-videoedit` with a reference does not use MiniMax `input_references` at all.** That facade only accepts `image_url` / `video_url` / `audio_url` (live create 400 on `video`, `job_01m163ththh5yer79dtmv0q85d`); the gateway then forwards the facade type unchanged into Wan's `input.media[].type`, which only accepts `video` / `reference_image` (live poll failure on `video_url`, `job_01m1608wr7hm49wzdggkynz6ay`). The published `/ai/v1/videos` `extra` field is ignored for this mapping. The shape that create+completed on a live credential (2026-08-29) is `POST /v1/videos` with `extra_body.input.media` (Wan's enum) — poll that task on `/v1/videos/{id}`, never `/ai/v1/tasks/{id}` (404). Do not merge product `GenerationRequest.extra` into `extra_body`. H3 stays on `/ai/v1/videos` with `video_url` / `image_url`. Incompatible duration/aspect/reference-mode get eliminated at the hard-filter routing stage — never left for the provider to error on. **Resolution is a client-facing ceiling (`480p`/`720p`/`1080p`/`2K`), not a must-match and not any one vendor's own spelling.** An omitted value (video remix) must not be treated as `2K` or a fabricated default, or cheaper edit models get a wrong tier. `RESOLUTION_TIER_MEMBERS` maps each studio tier to every vendor synonym (`720p` includes MiniMax H3's `768P`). After the final model is chosen, `adapt_resolution_tier` picks exact / highest strictly lower / last-resort lowest — never 1080p→2K — and `resolution_not_supported` only if that candidate maps to no studio tier. Costing and `nodes.execute_provider_generate`/`_sandbox_live_generate` send the adapted vendor literal. **The upstream request body's literal still never gets its casing normalised.** The hard filter still keys on the **model name** via the profile table (`minimax-h3` / `wan2.7-videoedit` / `doubao-seedance-2-5-260628`) — don't change it to key on `protocol` alone. `dmxapi_media.py` keeps its own, entirely separate profile table (`VideoModelProfile`/`ImageModelProfile`) for its five entries — four video models (`MiniMax-H3`, `MiniMax-H3-video_regeneration`, `doubao-seedance-2-5-260628`, `wan3.0-video`) plus one image model (`doubao-seedream-5-0-pro-260628`) — and its limits are not copies of AiHubMix's: DMXAPI's `MiniMax-H3` accepts only six aspect ratios (`21:9`/`16:9`/`4:3`/`1:1`/`3:4`/`9:16` — no `adaptive`/`3:2`/`2:3`/`9:21`, matching `model_catalog.py`'s entry) where AiHubMix's H3 accepts ten. The two providers never share a lookup, and `media_endpoints.py::dynamic_capabilities` picks which one to query purely off `endpoint.protocol`.
15. **Media `protocol` is an HTTP-contract standard name, not a gateway provider name.** The dropdown shows OpenAI / MiniMax / MiniMax V2 / ComfyUI / DMXAPI / fal, etc.; AiHubMix's image/audio API is OpenAI-compatible, so it shows as **OpenAI**. Implemented so far: `openai` (text-to-image, image-to-image, audio, and video via the OpenAI Videos API `/v1/videos`), `minimax` (AiHubMix's `/ai/v1/videos` facade via a per-model profile table — text-to-video/image-to-video/video-to-video, e.g. MiniMax H3), `minimax_v2` (official MiniMax Video V2 `POST /v2/video_generation` with `content[]` — Metaso's H3 channel; see invariant #19), `dashscope` (`_DASHSCOPE_CAPABILITIES = {video_analysis}` only — `AiHubMixMediaProvider.submit` routes `capability_tag == video_analysis` to `_submit_video_analysis`, a synchronous Qwen-VL `/v1/chat/completions` call), `dmxapi` (DMXAPI's own `/v1/responses` task envelope — the one deliberate exception to "never name a protocol after a vendor," since this specific envelope shape is DMXAPI's own invented convention rather than a shared standard; see invariant #18), `fal` (fal.ai queue `POST queue.fal.run/{app}` + `Authorization: Key` — MiniMax H3 Max; see invariant #20). `wan2.7-videoedit` is configured as `minimax` for catalog/profile limits, but a request that actually carries a reference is internally routed onto the OpenAI Videos path with `extra_body.input.media` (see invariant #14) — `protocol=openai` on that endpoint is not required. `comfyui` / `google` / `ark` / `kling` are catalogue placeholders only — an unimplemented protocol must never enter the `dynamic_capabilities` catalogue, and silently falling back to OpenAI is forbidden. `openai`, `minimax` and `dashscope` instantiate `AiHubMixMediaProvider`, branching internally by `protocol`/`capability_tag` (and, for Wan edit, by model+reference); `dmxapi` instantiates the wholly separate `DmxApiMediaProvider`; `minimax_v2` instantiates `MinimaxV2MediaProvider`; `fal` instantiates `FalMediaProvider` (`media_endpoints.py::_factory` dispatches on `protocol`) — these providers share no HTTP-shape code because each contract is a different request/response shape, not a `base_url` variant of another. `infer_media_protocol` still maps a video-generation-only endpoint to `minimax` (the AiHubMix facade) and is **code-blocked from ever inferring `minimax_v2` or `fal`** — those two are opt-in only, chosen explicitly by an operator, so inference can never silently rewrite an existing endpoint onto them.
16. **`AgentRun.node_id` is written back by the workflow engine — an agent function never sets it itself.** Before calling an executor, `WorkflowRunner._execute_node` records the prior value of `ctx.state["_last_agent_run_id"]`; after the executor runs, if that value changed (meaning this node produced a new `AgentRun`) and it isn't a `dry_run`, it runs a single `UPDATE ... SET node_id = :node_id` on that row — no agent function needs, or should, take a `node_id` parameter. The product sandbox is a real job (`dry_run=False`), so this write-back happens there too, as normal. `RoutingDecision.agent_run_id` follows the same pattern: `select_provider()`'s `AgentOutcome.agent_run_id` passes through into `RoutingDecision`, and `nodes.py::execute_route_score` sets it into `ctx.state["_last_agent_run_id"]` so this LLM call's routing score also attaches to the `route_score` node — without changing `intent_router.select_provider()`'s own call contract.
17. **The product sandbox uses real media providers, same as the consumer app.** The frontend `live_provider` toggle is gone from editor trial runs, but the `WorkflowContext.live_provider` field itself remains (`types.py`) for `dry_run` walks that still want a real provider call — that pair is what makes `_sandbox_live_generate` poll a pending video task synchronously in-process via `_poll_sandbox_pending` (`nodes.py`, capped by `_sandbox_poll_budget_ms`, `PROVIDER_TIMEOUT` on expiry, no `GenerationJob`/credits/`ProviderAttempt`); `WorkflowContext.dry_run` is otherwise reserved for unit-test graph walks. Never push a full prompt to the consumer-facing public SSE stream — admin review reads from `AgentRun.input_json` / `JobEvent.payload` instead.
18. **DMXAPI (`dmxapi_media.py`) is a second real media provider, independent of AiHubMix, speaking one unified `POST /v1/responses` envelope for everything** — a synchronous image family (`doubao-seedream-5-0-pro-260628`: text-to-image/image-to-image, the latter covering both a single-reference edit and 2–10 image "multi-image fusion") and an async submit-task-then-poll video family (`MiniMax-H3`, `doubao-seedance-2-5-260628`, `wan3.0-video`, and `MiniMax-H3`'s video-regeneration mode). The request/response *body* shape differs per model family, so `DmxApiMediaProvider` dispatches internally by `model` (`extract_task_id`/`_poll_result`/`_build_video_body` each branch on it), the same way `AiHubMixMediaProvider` dispatches by `capability_tag`/`protocol`. Polling reuses the same endpoint with the `model` swapped for that family's own `"{family}-get"` id (`MiniMax-H3-get` / `seedance-2-5-get` / `wan3.0-get`) and `input` holding the task id. **`MiniMax-H3-video_regeneration` only upscales a source clip that already meets MiniMax-H3's own 768P output spec (audio track, 24fps, dimensions divisible by 32, area ≤768×1344, 107–362 frames) to 2K — it is not a general user-video-editing capability**, and it cannot faithfully replay a past job's full original multi-modal input (the platform does not persist that), so `_build_minimax_h3_regeneration_body` only reconstructs the prompt plus the one `frame_type="base_video"` reference; anything beyond a plain-prompt original generation will fail upstream. That model also has no connectivity-safe probe body (`dmxapi_media.probe_video_body` raises for it) — `connectivity.py` must return `error_code="no_capability"` rather than guessing a request. **Seedance 2.5's create body (`_build_seedance_25_video_body`) is the one shape that has been exercised live** (fixed in `ce588dc` after a real 400): text and every reference go into `input` as `image_url`/`video_url`/`audio_url` items carrying a `role` (`first_frame`/`last_frame`/`reference_image`/`reference_video`/`reference_audio`), built by the shared `_content_items_from_references` — the same `input` array shape DMXAPI's `MiniMax-H3` uses — with **no top-level `input_references`/`frame_images`** (live `unsupported parameter: input_references`); a first-frame or first+last-frame task forces `ratio="adaptive"`, and frame roles and `reference_*` roles are mutually exclusive (`ValueError`). Tests: `back/tests/unit/test_dmxapi_media.py::test_seedance_25_multimodal_references_go_into_input` / `test_seedance_25_first_last_frame_go_into_input_with_adaptive_ratio`. The catalogue's `reference_modes` (`VideoModelProfile`) still spell `input_references`/`frame_images` — those are product-level hard-filter hints, not HTTP field names on this family. `wan3.0-video` alone uses a different envelope: `input.media[]` (its own `first_frame`/`last_frame`/`reference_*` `type` vocabulary via `_wan3_media_items`) plus a `parameters` block (`_build_wan3_body`). The MiniMax-H3 and Seedance poll field names are treated as confirmed from the docs (`_poll_result`: `task.status`/`task.content.url` vs top-level `status`/`output[].content[].text`); the `wan3.0-video` poll branch remains the least certain (completion inferred from a URL-looking `output[]` text unless `provider_metadata.task_status` says otherwise), and `MiniMax-H3-video_regeneration`'s reuse of `MiniMax-H3-get` is a documented guess. Polling also **classifies its own errors**: `_TERMINAL_POLL_ERROR_MARKERS` turns a DMXAPI 502 carrying `dmxapi_upstream_error` into `PROVIDER_TASK_FAILED` rather than leaving the task pending, so `route_score` excludes that provider on the retry instead of the job burning its wall clock waiting on a task the vendor has already given up on. A new poll branch must decide the same question — terminal or transient — explicitly; defaulting to transient is how a dead task turns into a timeout. Every response-parsing function still tolerates a few plausible shapes rather than betting on one, and says so in its docstring — fix the specific function (not the whole module) once a real call disagrees, same "verify before trusting the docs" posture as `_submit_qwen_image_edit`/`_uses_wan_openai_edit` in `aihubmix_media.py`. `VIDEO_RESOLUTIONS` (`platform_config/schemas.py`) had to widen to carry three vendors' differently-cased resolution strings side by side (`480p`/`720p`/`1080p` for DMXAPI's doubao models, `480P`/`720P`/`1080P` for `wan3.0-video`, `768P`/`2K` for MiniMax) — never normalise the casing, the upstream gateway matches on the literal string. `back/app/providers/model_catalog.py`'s `VENDOR_MODEL_CATALOG` (surfaced read-only via `GET /admin/llm-providers/catalog`) is a **pure admin-picker convenience** layered on top of this — a curated "service provider → known model" list that pre-fills `LlmProviderEndpointUpsertRequest` fields in `/admin/models`' `VendorModelPicker`, never itself validated against or enforced at save time; the free-text "custom" path (today's only behaviour before this catalogue existed) is unaffected and always available.
19. **Official MiniMax Video V2 (`minimax_v2_media.py`) is a third real media provider**, independent of both AiHubMix's `/ai/v1/videos` facade (`protocol=minimax`) and DMXAPI's `/v1/responses` envelope. Metaso (`https://metaso.cn/api/minimax`) is the first vendor on this contract; the HTTP shape is MiniMax's own V2, not a Metaso-specific protocol name. Create is `POST /v2/video_generation` with a required non-empty `content[]` text item (≤7000 chars) plus optional `image_url`/`video_url`/`audio_url` items carrying `role` (`first_frame`/`last_frame`/`reference_image`/`reference_video`/`reference_audio`). Text-only (t2va) remaps a studio `adaptive` ratio to `16:9` — official V2 400s on `adaptive` without media. First/last-frame (i2va) forces `ratio=adaptive`. Multimodal reference (r2va) is mutually exclusive with frame roles. Caps: ≤9 images, ≤3 videos, ≤3 audios, ≤12 files total. H3 profile (independent of AiHubMix's ten-ratio table): 4–15s, `768P`/`2K`, six official ratios plus `adaptive`. Create returns `{task_id}` (also tolerate `task.id` / top-level `id`); poll is `GET /v2/query/video_generation/{id}` and a succeeded task downloads `task.content.url` with a header-less client (presigned URL); cancel is `DELETE /v2/video_generation/{id}` (official V2 only cancels `queued`; a miss is logged and does not block local CANCELLED). **Query / cancel / download have not been verified against a live Metaso credential** — every parser tolerates a few plausible envelopes; fix the specific function, not the whole module, if a real call disagrees. First-period scope is MiniMax-H3 generate only (`text_to_video` / `image_to_video` / `video_to_video`); do not add 768P→2K regeneration (`/v2/video_regeneration`), H3-Context-IR, official/Metaso H3-Max, or Metaso's OpenAI `/v1/videos` compatibility layer (single-image only, Sora closing 2026-09-24). fal.ai's H3 Max channel is a different protocol (`protocol=fal`, invariant #20), not this V2 adapter. Tests: `back/tests/unit/test_minimax_v2_media.py`.
20. **fal.ai (`fal_media.py`) is a fourth real media provider**, independent of AiHubMix, DMXAPI, and official MiniMax V2. Auth is `Authorization: Key $FAL_KEY` (not Bearer). One catalog model `minimax/h3-max` (vendor `fal`, base `https://queue.fal.run`) dispatches to three fal apps by reference shape: no refs → `text-to-video`; only `first_frame`/`last_frame` images → `image-to-video` (`image_url`/`end_image_url`, omit `aspect_ratio` when a first frame is present); any generic image/video/audio ref → `reference-to-video` (`reference_*_urls`). Frame roles and generic refs are mutually exclusive; audio cannot be the only reference; at most 12 files. Profile (independent of AiHubMix/V2 H3): 5–15s (a 4s job is hard-filtered away, the global studio minimum stays 4), `480P`/`768P` (no 2K — `adapt_resolution_tier` drops 1080p/2K to 768P), six ratios plus `adaptive`. Text-to-video remaps studio `adaptive` to `16:9`. Always send `prompt_expansion_mode=balanced` and `enable_safety_checker=true`; never `sync_mode` or the `fal-client` SDK. Submit is `POST /minimax/h3-max/{route}`; `external_task_id` is `{route}#{request_id}` because fal ids are scoped per app. Poll is `GET .../requests/{id}/status` then, on `COMPLETED`, `GET .../requests/{id}/response` and a header-less download of `video.url`. `IN_QUEUE`/`IN_PROGRESS`/transient HTTP stay pending; `COMPLETED` with `error` is `PROVIDER_TASK_FAILED`. Cancel is `PUT .../requests/{id}/cancel` (`202` success; `400` already-completed / `404` return False and do not block local CANCELLED). Admin「验证有效」posts the cheap 480P t2v probe then best-effort cancels so a ping does not leave a billable render. **Queue submit/poll/cancel have not been verified against a live fal credential** — every parser tolerates a few plausible envelopes; fix the specific function, not the whole module, if a real call disagrees. Do not add official MiniMax H3-Max or Metaso H3-Max on this protocol. Tests: `back/tests/unit/test_fal_media.py`.

## Prompt & Model Binding

Each agent's `SYSTEM_PROMPT` has migrated to a versioned `AgentSkill`. Model binding is managed only through `/admin/models`'s `llm_providers` catalogue plus `/admin/agents`'s `AgentProfile`: judgment-role (`judgment`) and assist-role (`assist`) agents share the same form — manually choose a default provider, an optional backup provider, and a model both support; a non-default agent with empty sampling fields inherits its role's default `AgentProfile`. `assist` is just a semantic label for the `copy` role (generating/polishing copy, not a pass/fail judgment) and doesn't change how binding works. **There is no default model name in code**; an unbound agent's `complete()` raises `ProviderTemporaryFailure` immediately — it never guesses `models[0]` or hardcodes kimi/doubao/ling, and never returns a fabricated result.

The gateway **has no embedding model** — semantic search uses a local deterministic implementation (see `zaolang-discovery-search`).
